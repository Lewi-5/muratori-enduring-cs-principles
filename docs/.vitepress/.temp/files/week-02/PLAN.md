## Why this week exists

Week 1 ended with a question its exemplar report left open: how does the language's notion of *storage duration* differ from where an optimized object actually lives? Week 2 answers it with the vocabulary C11 supplies (object, object representation, alignment, storage duration, linkage, lifetime, effective type) and separates that vocabulary from what one ABI, compiler, or machine happens to do. The vehicle is a small **object-layout inspector**: a C tool that predicts and prints how a struct's members are placed and draws that placement as a byte map. The habit from week 1 continues and becomes central: **draw the memory before running the program, then reconcile the drawing with the observation.**

By the end, a learner should be able to explain alignment and padding and compute a struct layout by hand; state what C guarantees about layout and what the reference System V x86-64 ABI specifies; place typed objects inside one aligned block without violating alignment or effective-type rules; distinguish automatic, static, and allocated storage and know when a pointer's value stops being usable; explain why an index survives relocation when a pointer does not; and separate *linkage* (which names refer to one object) from *storage duration* (how long an object lives) using object-file symbols. The Computer, Enhance! “Instructions Per Clock” entry supplies motivation only: after wasted work is removed, the same necessary work can still run at different speeds. This week measures no speed. It records what byte-and-offset facts *cannot* tell you, which prepares weeks 21–29.

Do not add later-week topics: arena or free-list allocators (weeks 17–18), page mapping and page faults (19), cache lines and false sharing (22, 37), array-of-structs versus struct-of-arrays timing (23), SIMD, atomics, `_Thread_local` storage (36), or a Haversine processor. E07's block-carving is a layout exercise, not an allocator design.


## Corrections incorporated after review

- **S01:** Descending alignment is optimal throughout the specified layout model, not only for scalar members. The answer key must prove this and distinguish constraints outside that model.
- **E05/E06:** Check additions as well as products. Counter increments have checked exhaustion behavior; no example may rely on signed overflow. Sequence calls before printing their results.
- **E07:** Bound capacity by `UINT32_MAX`; specify zero-size and zero-capacity policies and initialized field values. Output pointers and the block remain unchanged on rejection. The block must be live allocated storage without a declared type, not a declared byte array; output objects must be valid and disjoint from that storage.
- **Alignment boundary:** Numeric `uintptr_t` divisibility and mandatory 64-byte extended alignment are reference-platform experiments, not portable C11 facts. Gate E07's target observations too. Do not pass arbitrary powers of two to the original C11 `aligned_alloc` contract; use the documented whitelist. Fundamental alignment remains distinct from extended alignment. A forced skip build tests gating, not another ABI.
- **E08:** Index stability requires preserved slot identity. File formats also require explicit encoding, bounds and version rules; byte-copying a struct is not portable serialization.
- **E01:** The two-digit formatter has an explicit `CHAR_BIT == 8` precondition; on other targets it rejects and the demo reports a skip. Exact-width typedefs and `uintptr_t` are requirements of the reference environment.
- **P01/P05:** A `buf + 1` cast is not automatically misaligned on every conceivable implementation; explain the conditional alignment rule. Declared byte storage still has a distinct effective-type restriction even when aligned. `calloc` promises zero bits, not every type's semantic zero.
- **Workload:** Use typed, warning-clean TODO scaffolds and supplied demo drivers, especially for E07/E08 and CLI plumbing. Implement the mechanisms in the TODO functions. No shared header supplies the alignment/layout answers. Target ten core hours, allow optional work beyond that, and mark the estimate unpiloted.

## Deliverable and working environment

The single graded assignment is an **object-layout inspector notebook**: ten small C programs that build up the inspector's parts, their tests, and a short report whose central content is *predicted memory drawings versus observed output*. As in week 1, the answer key must answer every learner-facing “explain,” “predict,” “draw,” “compare,” and “interpret” request as well as every coding task. This file remains the specification for that work.

- Reference environment: x86-64 Linux (or Ubuntu under WSL), GCC and Clang, C11, `make`, the standard C library, and binutils (`nm`, `readelf`, `objdump`, `size`). Python 3 only orchestrates tests. Feature-test macros are needed only if a POSIX function is used; this week should need none.
- Required development build: `-std=c11 -Wall -Wextra -Wpedantic -Werror -O0`, with an `-O2` build also passing every test. Instructor verification adds an AddressSanitizer/UndefinedBehaviorSanitizer configuration on both compilers. Each exercise compiles independently. E09 compiles as separate translation units and links. Later exercises may copy helpers the learner wrote earlier; there is no shared learner library. The package does not solve E02 in a supplied header.
- Every exercise is a standalone `exNN.c`, except E09 (`ex09_main.c`, `ex09_data.c`, `ex09_data.h`). As in week 1, the public C harness includes each exercise source with its `main` renamed, so the named functions and types are part of the contract. Output examples in the prompts are exact except fields explicitly marked as observed.
- Tests verify portable relationships and explicit-input arithmetic. They must not hard-code `sizeof`, `_Alignof`, offsets, padding, pointer width, byte order, addresses, or any timing. **Target-specific checks must be labelled separately:** E03/E10 compare the natural-alignment model with compiler layout, gated to LP64 x86-64 Linux, and report “skipped” elsewhere. These document reference-target properties, not C11 guarantees. `nm` letters and section names (E09, S02) are toolchain observations and are not part of the automated pass/fail tests.
- Keep executable examples defined: no dereference, comparison, or printing of a pointer whose object's lifetime has ended (take a `uintptr_t` snapshot while the object is alive if a later comparison is wanted); no misaligned pointer is ever *formed* (test alignment on the integer address, then cast); no out-of-bounds access; no reliance on padding contents; no access to a declared `char` array through a struct lvalue. - The playground is the E03/E04 pair: add, remove, or reorder members in the specified lists, predict the size and byte map on paper, run, and reconcile. It feeds the notebook rather than adding a second graded assignment.

## Practice problems and stretch work

The weekly package must include these **six ungraded practice problems**, with answer keys separate from the learner prompt:

1. Classify five statements as portable C11 guarantees, System V/implementation-defined observations, unspecified values, or undefined operations, and justify each: `sizeof(struct S) % _Alignof(struct S) == 0`; `offsetof(struct {char c; double d;}, d) == 8`; reading a struct's padding bytes through `unsigned char`; converting `buf + 1` of a `char buf[8]` to `int *`; using `memcmp` to prove two structs with equal members are equal.

3. Compute by hand the offsets, size, and alignment of a six-member struct using the E03 rule and stated member sizes and alignments, then reorder its members to reduce size and count the bytes saved. Verify with the inspector afterward.
4. For `struct Rec recs[5]`, state the value and type of `&recs[4] - &recs[1]`, which of `&recs[5]` and `&recs[6]` may be formed, what `==` and `<` between pointers into different arrays mean, and the byte distance between `&recs[3]` and `&recs[1]`.
5. Given a 256-byte block from `malloc`, from a declared `char buf[256]`, and from a declared `_Alignas(max_align_t) unsigned char buf[256]`, decide which may be accessed through a `struct State *` and why (alignment and effective type). Give repairs, including `memcpy` into a declared `struct State`. Relate the answer to the platform block in the Handmade Hero 014 talk.
6. Compare pointer links and index links in a table under three events: growth by `realloc`, saving to and loading from a file, and copying the table for an undo snapshot. Say which links stay valid, what each option costs, and why slot zero is reserved.
