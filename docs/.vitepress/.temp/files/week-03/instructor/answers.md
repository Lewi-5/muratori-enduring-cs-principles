# Worked answers — numbers in a box

The linked C files are complete annotated implementations, not pseudocode. Each coding answer explains correctness, the boundary cases and a plausible faulty approach; each question answer supplies the reasoning independently of test output. Every mathematical claim below is either proved in the text or reproduced by a recorded run of [extras/measure.c](extras/measure.c), [extras/stretch_antipodal.c](extras/stretch_antipodal.c) or the contract suites, and **measured values are labelled as measured** (GCC 11.4 and Clang 14, glibc 2.35, x86-64 Linux/WSL2, `-ffp-contract=off`, identical at `-O0` and `-O2`; see [validation.md](validation.md)). They are one machine's results, not constants. Authority labels: **C11** (N1570), **Annex F / IEC 60559**, **glibc/libm**, **compiler**, **measured**.

Clauses used, checked against the N1570 text: §6.4.4.2 ¶3 (a decimal floating constant is the nearest representable value *or an adjacent one*, implementation-defined); §7.12.10.1 ¶3 (`fmod` returns `x − ny` for an integer `n`, same sign as `x`, magnitude below `|y|`); **§F.10.7.1 ¶2 (“the returned value is exact”)**; §F.3 (the relational and equality operators provide IEC 60559 comparisons); §F.5 (decimal↔binary conversion is correctly rounded); §F.7 (a contracted expression is rounded once); §5.2.4.2.2 (`FLT_EVAL_METHOD`). **A correction to the source plan:** the `fmod(3)` manual page does *not* state that the result is exact (checked on 2026-09-20); the guarantee comes from ISO C Annex F. This package cites Annex F.

### E01.C

[ex01.c](src/ex01.c) checks the reference-platform gate and the output pointer first, copies the eight bytes of the `double` into a `uint64_t` with `memcpy`, and extracts the fields by shifting and masking unsigned 64-bit values: sign `bits >> 63`, exponent `(bits >> 52) & 0x7FF`, fraction `bits & (2^52 − 1)`. The class follows from the two fields: exponent 0 with fraction 0 is zero, exponent 0 with nonzero fraction is subnormal, exponent 2047 with fraction 0 is infinite, exponent 2047 with nonzero fraction is NaN, and everything else is normal. The result is built in a local `DoubleParts` and assigned to `*out` only at the end. `compose_double` validates `sign <= 1`, `exponent <= 0x7FF` and `fraction < 2^52`, assembles `((uint64_t)sign << 63) | ((uint64_t)exponent << 52) | fraction` and copies the bytes back with `memcpy`.

Verified values under the gate: `1.0` is exponent 1023 fraction 0; `0.5` exponent 1022; `-2.0` sign 1 exponent 1024; `0.1` exponent 1019 fraction `0x999999999999A`; `-0.0` sign 1 exponent 0 fraction 0; `DBL_MIN` exponent 1 fraction 0; `DBL_TRUE_MIN` exponent 0 fraction 1; `DBL_MAX` exponent 2046 fraction `0xFFFFFFFFFFFFF`; infinity exponent 2047 fraction 0. The quiet NaN produced by `NAN` printed sign 0, exponent 2047, fraction `0x8000000000000` on this machine, but **that payload and sign are an observation** and the tests assert only class and exponent. A faulty version writes `(uint64_t)exponent << 52` as `exponent << 52` with `exponent` an `unsigned`: the shift count equals or exceeds the width of a 32-bit type, which is undefined behavior, and the top bits vanish. The other faulty version is `*(uint64_t *)&value`; see E01.Q. Rejection paths are tested with sentinel outputs that must not change, and the forced-skip build (`-DGEO_FORCE_NO_IEC`) confirms both functions reject.

### E01.Q

For a normal number the value is (−1)^s × 1.f × 2^(e−1023), where `f` is the 52-bit fraction and the leading 1 is implicit. Exponent 0 means subnormal: 0.f × 2^−1022, which fills the gap between zero and `DBL_MIN` with spacing 2^−1074 so that `x − y == 0` exactly when `x == y` (gradual underflow). Exponent 2047 encodes infinity (fraction 0) and NaN (fraction nonzero). Zero has two encodings because the sign bit is independent of the value; IEC 60559 says they compare equal, and they differ only in operations such as `1.0 / -0.0`, which is −infinity. A NaN compares unordered with everything including itself, so `x != x` is true exactly when `x` is NaN.

`0.1` is not representable because 1/10 in binary is 0.0001100110011…, repeating. Normalized it is 1.100110011…₂ × 2⁻⁴ (biased exponent 1019). The 52 fraction bits are the repeating pattern `1001`, i.e. `0x9999999999999`, and the discarded bits continue `1001…`: the first is 1 and more nonzero bits follow, so the value rounds **up** and the stored fraction ends in `A`: `0x999999999999A`. The exact stored value, from 60-digit decimal arithmetic in the validation run, is 0.1000000000000000055511151231257827…, slightly above one tenth.

What is guaranteed by what: C11 §5.2.4.2.2 describes a *model* of floating types and does not fix the format; §6.4.4.2 ¶3 even lets an implementation pick a value adjacent to the nearest for a decimal constant. Annex F (`__STDC_IEC_559__`) binds the implementation to IEC 60559 and §F.5 makes the conversion correctly rounded. That the fields printed above are what this machine produced is an **observation**, gated by `DBL_MANT_DIG == 53`, `DBL_MAX_EXP == 1024`, `CHAR_BIT == 8` and `__STDC_IEC_559__`. `memcpy` copies an object representation legally. `*(uint64_t *)&value` accesses a `double` object through an lvalue of type `uint64_t`, which C11 §6.5 ¶7 (effective type) does not permit, so an optimizer may assume the two do not alias and reorder or drop the read; it may also be misaligned. Compilers turn the `memcpy` into a single register move, so nothing is lost.

### E02.C

[ex02.c](src/ex02.c). `approx_equal` validates the tolerances and output pointer first (`isfinite` and sign checks, so `-0.0` is accepted as a tolerance because it is not negative). Then the order matters: a NaN operand answers 0; `a == b` answers 1 and covers equal infinities and `+0`/`−0`; any remaining infinity answers 0 (otherwise `inf − finite` would be infinite and `inf <= inf` would wrongly succeed); the difference is computed and if it overflowed to infinity the answer is 0 *by contract* (for `DBL_MAX` and `−DBL_MAX` the true difference exceeds the largest double, and the contract chooses “not equal” instead of an ambiguous infinity comparison); finally `diff <= max(abs_tol, rel_tol * max(|a|, |b|))`. Explicit NaN handling is documentation more than logic: NaN comparisons are false anyway, so a mutant without that line is behaviorally equivalent (recorded in the validation mutation table).

`ulp_distance` maps each finite double to an unsigned key so that key order equals numeric order. With `magnitude = bits & 0x7FFFFFFFFFFFFFFF` and `Z = 2^63`, the key is `Z + magnitude` for sign 0 and `Z − magnitude` for sign 1. Then `+0.0` and `−0.0` both map to `Z`, as the contract requires, the key of `DBL_TRUE_MIN` is `Z + 1`, and the key of `−DBL_TRUE_MIN` is `Z − 1`, so those two are 2 apart and each is 1 from zero. The distance is the larger key minus the smaller key, in unsigned arithmetic, and cannot overflow: the largest magnitude is `0x7FEFFFFFFFFFFFFF`, so `DBL_MAX` to `−DBL_MAX` is `0xFFDFFFFFFFFFFFFE`, which fits. `add3_left` and `add3_right` differ only in parentheses; with `-ffp-contract=off` and no reassociation flags the compiler may not change the grouping. Driver output (measured): `left=0.60000000000000009 right=0.59999999999999998 ulps=1` and `sum=0.30000000000000004 target=0.29999999999999999 ulps=1`.

Faulty approaches: subtracting the raw bit patterns as signed integers (sign-magnitude representation makes negative numbers order backwards, and `−0.0` becomes a huge negative number); or mapping negatives as `~bits` without special-casing zero, which counts `−0.0` and `+0.0` as two apart and shifts every negative distance by one. The harness catches both (mutation table).

### E02.Q

Absolute error is `|a − b|`; relative error is `|a − b| / |b|`; ulp error counts representable doubles between them. Worked numbers: near 1 the spacing is 2^−52 = 2.22e−16; near 180 it is 2^−45 = 2.84e−14; near 1e300 it is about 1.5e284, so `fabs(a − b) < 1e-9` there accepts only `a == b`. Near 1e−20 the same test accepts everything within 1e−9, so `1e-20` and `2e-20`, which differ by 100 percent, compare “equal”. That is the two-way failure of a fixed absolute tolerance: inputs `(1e-20, 2e-20)` wrongly equal, and `(1e300, 1e300·(1 + 1e-15))` wrongly unequal, since the difference is about 1e285. A relative tolerance alone fails when one operand is zero. So the contract combines them, `max(abs_tol, rel_tol · scale)`, and the caller chooses both from knowledge of the problem.

Why `0.1 + 0.2 != 0.3`: the exact values are 0.1 = 0.1000000000000000055511…, 0.2 = 0.2000000000000000111022…, so the exact sum is 0.3000000000000000166533…. The two doubles nearest to it are 0.299999999999999988897… (which is the double `0.3`) and 0.3000000000000000444089…, and the exact sum is **exactly halfway** between them (each is 2.7755575615628914e−17 away). Round-half-to-even picks the one with an even significand, the upper one, so the sum prints as `0.30000000000000004`, one ulp above the double `0.3`. This is an Annex F (IEC 60559) property, verified by exact decimal arithmetic and by running. Association: `(0.1 + 0.2) + 0.3` = 0.6000000000000001 while `0.1 + (0.2 + 0.3)` = 0.6 (`0.2 + 0.3` is exactly 0.5), one ulp apart. The extreme case `(1e16 + −1e16) + 1` is 1 but `1e16 + (−1e16 + 1)` is 0, because `−1e16 + 1` is not representable and ties to `−1e16`: addition is not associative, so a compiler that regrouped it would change results, which is why `-ffast-math` is forbidden here.

Zero and infinity: `+0` and `−0` are numerically equal, so they are 0 ulps apart; infinity has no finite ulp distance and is rejected instead of inventing one; NaN has no order. `==` on computed doubles is a design decision: it is right for exactly representable results such as `sqrt(4)`, selected `fmod` and integer-valued calculations, and copies and sentinels. Under Annex F, `sqrt` is correctly rounded, but `sqrt(2)` is inexact because its mathematical value is irrational. Correct rounding does not make different computational paths bit-identical. Transcendental results need a justified error tolerance.

### E03.C

[ex03.c](src/ex03.c). `deg_to_rad` multiplies by `GEO_PI / 180.0`; `rad_to_deg` by `180.0 / GEO_PI`. Each has two roundings in the constant and the product, so a round trip has a worst-case relative error of about four half-ulps (≈ 4.4e−16); measured maximum on the test lattice was 2.2e−16, and the tolerance is 1e−15. `wrap_lon_deg` computes `r = fmod(lon, 360)`; if `r >= 180` it subtracts 360 and if `r < −180` it adds 360. `lon_delta_deg` validates that both longitudes are in `[−180, 180]`, subtracts and wraps: `to − from` may round (its operands can differ in magnitude), by at most half an ulp of a number below 360, about 2.8e−14 degrees, and the wrap itself is then exact. `(179, −179)` gives 2, `(−179, 179)` gives −2 and `(0, 180)` gives −180 by the half-open policy.

`sin_deg` and `cos_deg` use one shared exact quadrant reduction. Work with `|x|` (symmetry is then applied, not computed, so oddness and evenness are exact): `r = fmod(|x|, 360)`, then subtract 270, 180 or 90 when `r` is at least that multiple, recording the quadrant `q`; the residue is in `[0, 90)`. Then sine uses `sin(r)`, `cos(r)`, `−sin(r)`, `−cos(r)` for `q = 0…3` and cosine uses `cos(r)`, `−sin(r)`, `−cos(r)`, `sin(r)`. At exact multiples of 90 the residue is exactly 0, and `sin(0) = 0`, `cos(0) = 1` are exact, so the outputs are exactly `0` or `±1` for every representable multiple including `9.0e15` (which is an exact multiple of 360). Because `−0.0` could otherwise appear (`−sin(0)`), a helper returns `+0.0` for any zero result. Faulty: `sin(deg_to_rad(x))` at 180 gives `1.2246467991473532e-16`, not 0.

Tests derive expectations independently: `wrap_lon_deg` is compared, on thirteen huge integer-valued doubles including `1e300`, `1e22`, `±2^60` and `DBL_MAX`, with `(m · 2^k) mod 360` computed by modular exponentiation in `uint64_t`, which never calls `fmod`. The `2^60` remainder is 136, illustrating that the remainder need not be a multiple of the input's spacing (256). These examples illustrate, but do not prove, the Annex F guarantee for every input. Measured accuracy against a `long double` reference over 3,897 lattice angles: maximum absolute error 1.48e−16 (tolerance 1e−15; the derivation is in E03.Q).

### E03.Q

Policy: mapping the circle to `[−180, 180)` needs one endpoint included and the other excluded to be a function. Choosing `−180` for the antimeridian is a convention (the other half-open choice gives `+180`); nothing about the globe prefers one. Both spellings name the same meridian, which is why E05 must give equal distances for them.

Why `fmod` is exact here: C11 §7.12.10.1 ¶3 defines the result as `x − ny` for an integer `n`, same sign as `x`, magnitude below `|y|`, and **Annex F.10.7.1 ¶2 guarantees an exact result when subnormal results are supported** on an IEC 60559 implementation. For finite binary64 `x` and divisor 360, if `|x| < 360`, the remainder is `x`. Otherwise write `|x| = m·2^e` with integer significand `m < 2^53` (allowing negative `e` for tiny values). If `e ≤ 3`, 360 is an integer multiple of `2^e`, so the remainder is `k·2^e`; because its magnitude is below 360 ≤ `|x|`, `|k| < m`, and it fits in binary64. If `e > 3`, both `x` and 360 are multiples of 8, so their remainder is a multiple of 8 with magnitude below 360 and is exactly representable. The sign of a negative `x` changes only the sign of this representable remainder. This is consistent with the Annex F guarantee; the finite oracle samples illustrate it without proving it universally. In particular, `fmod(2^60, 360) = 136`, not a multiple of the input spacing 256.

The single correction is exact by **Sterbenz's lemma: if `y/2 ≤ x ≤ 2y` then `x − y` is exact.** When `r ∈ [180, 360)`, take `x = r` and `y = 360`: `180 ≤ r ≤ 720`, so `r − 360` is exact, and its value lies in `[−180, 0)`. When `r ∈ (−360, −180)`, `r + 360 = 360 − |r|` with `|r| ∈ (180, 360)`, again within a factor of two of 360. The same lemma covers the quadrant subtractions in E03.C: `r − 270` for `r ∈ [270, 360)`, `r − 180` for `[180, 270)`, `r − 90` for `[90, 180)`; in each case the subtrahend `k` satisfies `r/2 ≤ k ≤ 2r`, so no rounding occurs.

`sin(GEO_PI)`: `GEO_PI` is the double nearest π, 3.141592653589793115997963…, which is **below** π by ε = π − `GEO_PI` = 1.2246467991473531772e−16 (60-digit decimal arithmetic). Then `sin(GEO_PI) = sin(π − ε) = sin ε = ε − ε³/6 + …`, and ε³/6 is about 3e−49, invisible. So the prediction is positive and 1.2246467991473532e−16, and the measured glibc 2.35 result was exactly `1.2246467991473532e-16`, agreeing with the derivation in all 17 digits shown. That the last digits agree on this machine is an observation about glibc; the portable statement is that it is small, positive, and about 1.2e−16.

`sin_deg(x)` versus `sin(deg_to_rad(x))`: the latter has already rounded π/180 and the product, so at 180° it evaluates sine at the wrong argument by ε. Use `sin_deg`/`cos_deg` for coordinate work, where axes and poles must be exact; use plain `sin`/`cos` when the input is already a radian angle (for instance the output of `atan2`). Half-open interval, again: `wrap(180) = −180`.

Faulty `lon − 360 * floor((lon + 180) / 360)`: the addition `lon + 180` rounds. For `lon = nextafter(180, 0) = 179.99999999999997` the sum is exactly halfway between two doubles and ties to 360.0, so `floor` returns 1 and the result is `−180.00000000000003`, **outside the range**. For `lon = 1e22` it returns 0 where the correct wrapped value is −80. Both measured (`recorded faulty_floor_wrap` lines in [validation.md](validation.md)); the harness kills a mutant with this formula.

### E04.C

[ex04.c](src/ex04.c). `vec3_dot` and `vec3_cross` are the textbook formulas; for small integer components every product and sum is exact, so `dot(a, cross(a, b))` is exactly 0. `vec3_length` finds `m = max(|x|, |y|, |z|)`; if `m == 0` the length is 0; otherwise it divides each component by `m` (all now at most 1 in magnitude), so the sum of squares is in `[1, 3]` and cannot overflow, and a component that underflows to zero after scaling is negligible next to 1. The length is `m * sqrt(sum)`, rejected only when that product is not finite. `vec3_normalize` uses the same scaling and then divides by the scaled length (in `[1, √3]`), so it never needs the unscaled length to be representable: `(DBL_MAX, DBL_MAX, 0)` normalizes to `(0.7071…, 0.7071…, 0)` while its `vec3_length` is rejected because `DBL_MAX · √2` overflows.

`latlon_to_unit` validates finiteness and the ranges, then multiplies exact-quadrant cosines and sines: `x = cos φ cos λ`, `y = cos φ sin λ`, `z = sin φ`. At `φ = ±90`, `cos_deg` is exactly 0 (and `+0`), so `x = y = 0` for every longitude and `z = ±1` exactly. `unit_to_latlon` first normalizes (so any finite nonzero vector is accepted, including one whose components would overflow `hypot`), computes latitude from `atan2(u.z, hypot(u.x, u.y))`, converts to degrees, and clamps to `[−90, 90]` (a conversion can round slightly above 90). It computes longitude from **the original** `atan2(v.y, v.x)` and wraps by the E03 rule; only original `v.x == v.y == 0` gives longitude 0. Scaling can underflow tiny nonzero horizontal components, so using normalized components for longitude would lose a recoverable direction: `(1e−200, 1e−200, 1e200)` must give 45°, even though latitude rounds to 90°. Round trip on a 35×71 degree lattice away from the poles (historical measurement): maximum latitude error 7.1e−15°, maximum wrapped longitude error 2.8e−14°, tolerance 1e−12°. A faulty normalization that divides by `sqrt(x*x + y*y + z*z)` fails four ways: overflow gives infinity so the result is `(0, 0, 0)`; underflow gives 0 so it divides by zero; `(DBL_MAX, DBL_MAX, 0)` overflows; and the zero vector is not rejected.

### E04.Q

A latitude/longitude pair gives two angles in a nonlinear spherical coordinate system, **not** coefficients in a linear basis. The map to a unit vector gives Cartesian components `x = cos φ cos λ`, `y = cos φ sin λ`, `z = sin φ` in the chosen fixed orthonormal basis: e₃ points through the north pole and e₁ through longitude 0 on the equator. For an actual basis change, use `b1 = (3/5, 4/5, 0)`, `b2 = (−4/5, 3/5, 0)`, `b3 = (0, 0, 1)` and `v = (1, 2, 3)`. Each basis vector has squared length 1, and all pairwise dot products are 0. Therefore its coordinates in this basis are `v·b1 = 11/5`, `v·b2 = 2/5`, `v·b3 = 3`; reconstruction gives `(11/5)b1 + (2/5)b2 + 3b3 = ((33−8)/25, (44+6)/25, 3) = (1, 2, 3)`. Dot products recover coefficients **because this basis is orthonormal**; a nonorthonormal basis needs a different method. These rational calculations are exact on paper, while C's binary64 approximates fifths. This is the basis-vector and dot-product operation developed in the assigned HH090–091 segments. For unit vectors `u·v = cos(central angle)`.

Naive length: `x*x` with `x = 1e200` is `+inf`, so `(1e200, 1e200, 0)` has “length” infinity; `x*x` with `x = 1e−200` underflows to 0, so `(1e−200, 0, 0)` has “length” 0 and normalization divides by zero. (Both reproduced by running.) Scaling by the largest magnitude prevents both because every scaled square is in `[0, 1]`. Normalization can succeed when the length is unrepresentable because the direction is `v/m` divided by a length of at most √3; the unscaled length is never formed.

Pole convention: only when the **original** `x = y = 0` is longitude undefined, and the contract returns 0 rather than depending on `atan2(0, 0)` and signed zeros. A latitude that rounds to 90° does not make nonzero original horizontal components an exact pole. Near the pole longitude is ill-conditioned (an error ε in `x` or `y` becomes an error ε / cos φ in longitude), so ordinary round-trip tests avoid asserting longitude there; the new regression checks a known recoverable longitude from the original inputs. Zero-length: a zero vector has no direction, so normalization must either reject it or invent a direction; Handmade Hero 047 has a Q&A segment specifically on zero-length normalization (the assigned 1:10:42–1:12:54), and this package's answer is a stated contract: reject and leave the output unchanged, rather than return a silent NaN.

### E05.C

[ex05.c](src/ex05.c) implements the three formulas. **Haversine:** `a = sin²(Δφ/2) + cos φ₁ cos φ₂ sin²(Δλ/2)`, clamp `a` to `[0, 1]`, angle `2·asin(√a)`. **Vector:** `u`, `v` from `latlon_to_unit`, angle `atan2(|u × v|, u · v)`. **Law of cosines:** `acos(clamp(sin φ₁ sin φ₂ + cos φ₁ cos φ₂ cos Δλ, −1, 1))`. All three validate the inputs first, and the distance is the angle times `GEO_EARTH_RADIUS_KM` (a model constant). Measured errors against analytic references (GCC 11.4, glibc 2.35, one machine; the identical coordinates are (40, 33.25), chosen because at mid-latitudes the cosine sum is not always exactly 1):

Tolerance: haversine and vector are asserted within relative 1e−12 (or absolute 1e−9 km when the expected value is 0); the largest observed relative error was 4.3e−15, so the margin is 230×. The law of cosines is asserted only to be finite and nonnegative: its error is recorded, not bounded, because bounding it would mean asserting a number this machine happened to produce. Lattice checks over 169 points (all 28,561 ordered pairs, and all 4,826,809 triples for the triangle inequality) found no NaN, all distances in `[0, π·R]`, symmetry error 0, triangle violation at most 1.5e−11 km (haversine) and 4.3e−12 km (vector); tolerances 1e−9 and 1e−8 km. Distances to `(lat, 180)` and `(lat, −180)` differ by at most 5.5e−12 km for the haversine path and exactly 0 for the vector path (because `sin_deg`/`cos_deg` are exact at ±180). The plain-libm haversine gives 6.8e−13 km between (90, 0) and (90, 120), the same point, because `cos(deg_to_rad(90))` is 6.1e−17 and not 0; the vector path with `cos_deg(90) = 0` gives exactly 0. Nothing here claims agreement with a real geodesic: the sphere is a model.

### E05.Q

Derivation (see P04): with unit vectors `u`, `v` and central angle `c`, `u · v = cos c`, and `|u − v|² = 2 − 2cos c = 4 sin²(c/2) = 4 hav(c)`. Expanding `u · v` with the coordinates and using `cos(Δλ) = 1 − 2 hav(Δλ)` gives `hav(c) = hav(Δφ) + cos φ₁ cos φ₂ hav(Δλ)`.

The clamp: in floating point `a` can land above 1. Recorded run (`measure.c`, both compilers, both levels): for the exact antipodes `(L, 0)` and `(−L, 180)` with integer `L = 1…89`, `a` exceeds 1 for `L = 8, 12, 82` (3 of 89) by exactly 2.22e−16, one ulp. The function `asin(sqrt(a))` produced **no NaN** on these samples: `(1 + 2^−53)^2 = 1 + 2^−52 + 2^−106 > 1 + 2^−52`, so `1 < sqrt(1 + 2^−52) < 1 + 2^−53`; round-to-nearest binary64 gives 1 without a tie. The alternative form `2·atan2(√a, √(1 − a))` produced NaN for all three, since `1 − a` is negative. Keep the clamp for the interface guarantee across permitted inputs, rounding environments and libm implementations. The sampled lack of NaNs for this `asin` form, including 4.5 million random valid samples, does not establish that removing its clamp is universally equivalent. The harness kills an `atan2` mutation without the clamp and accepts the valid `atan2` form with the clamp.

Conditioning: if the final function is `c = g(s)` and `s` carries an absolute rounding error δ, then `c` carries about `|g′(s)| · δ`. **Law of cosines:** `c = acos(x)`, `|g′| = 1/√(1 − x²) = 1/sin c ≈ 1/c` for small `c`. The doubles just below 1 are 1.1e−16 apart, so `x` can be off by at least 5.5e−17: the resulting error in `c` is about 5.5e−17/c. For `c = 1.75e−7` rad (one metre) that predicts 3.2e−10 rad, and the measured error was 1.2e−10 rad (7.6e−7 km / 6371), the same order and under the bound. For identical points `x` can round to 1 − 1.1e−16, giving `c = √(2 · 1.1e−16) = 1.49e−8` rad = 9.49e−5 km, exactly the measured value. So the law of cosines is ill-conditioned for small angles even though the formula is algebraically correct. **Haversine:** `c = 2 asin(s)`, `|g′| = 2/√(1 − s²)`, near 2 for small `c`, so it is well conditioned there; but it blows up as `s → 1`, the antipodal region. **Vector:** `atan2(y, x)` is well conditioned everywhere except at the origin. Measured haversine error at exact antipodes: up to 1.9e−4 km (relative 9.5e−9), at L = 3, while the vector formulation was exact; hence the claim in the prompt that E05 does not assert accuracy near antipodes, which S02 measures.

The oracle: analytic values derived from the inputs (arc = R · angle in radians; `one_km_meridian` uses the latitude difference 180/(π·R) degrees), plus lattice properties (symmetry, range, triangle inequality) that any correct distance must satisfy independent of the formula.

### E06.C

[ex06.c](src/ex06.c). Validate the domain first: each coordinate finite with `|c| ≤ 2^25` (`fabs(NaN) <= limit` is false, so NaN is rejected too). Degenerate segments are handled first, by cases: both points (equal or not), a point on a segment (`on_segment` tests orientation zero and lexicographic containment), then the general case. With `d1 = p1 − p0`, `d2 = q1 − q0`, `w = q0 − p0`, `denom = cross(d1, d2)`. **The parallel test happens before any division.** If `denom ≠ 0`: `tn = cross(w, d2)`, `un = cross(w, d1)`; after flipping signs so `denom > 0`, the intersection lies on both closed segments exactly when `0 ≤ tn ≤ denom` and `0 ≤ un ≤ denom`. If `tn` is 0 or `denom` the answer is `p0` or `p1` exactly; if `un` is 0 or `denom` it is `q0` or `q1`; otherwise the point is `((p0.x·denom + tn·d1.x)/denom, …)`, a single division. If `denom = 0` and `cross(w, d1) ≠ 0` the lines are parallel and distinct (`SEG_NONE`); otherwise they are collinear, and the closed overlap is found by lexicographic ordering of the endpoints: the overlap is from the larger of the two lower endpoints to the smaller of the two upper endpoints; empty if inverted, a point if equal, otherwise `SEG_OVERLAP`. Lexicographic order is monotone along any line, so no axis choice is needed. Outputs are written last.

Exactness is checked, not assumed: the **supplied** C harness compares kind and point over all 6,561 ordered pairs of segments from the nine lattice points `{0,1,2}²` with an independent integer oracle (below). Learners run and explain this infrastructure, trace one case, and add a few purposeful boundary tests; they do not implement a second exhaustive oracle. Crossing points are within 4e−16 of the exact rational (historical measured maximum 8.9e−17, consistent with the half-ulp bound of 1.1e−16 for a value below 2), and every true integer or half-integer result is bit-exact. The three kinds all occurred (the harness asserts each branch was exercised). The domain corner case `(−2^25, −2^25)–(2^25, 2^25)` against `(−2^25, 2^25)–(2^25, −2^25)` returns exactly `(0, 0)`, where the intermediate values reach 2^53. A non-integer T-junction, `p0 = (0.2, 2.3)` on the segment `(−0.8, 2.3)–(1.2, 2.3)`, must return `(0.2, 2.3)`; recomputing it from the parametric formula gives `y = 2.3000000000000003`, and a mutant without the exact-endpoint branch fails this test.

### E06.Q

Orientation: `cross(b − a, c − a)` is positive, zero or negative as `c` is left of, on, or right of the directed line `a → b`; two segments properly cross when each one's endpoints lie strictly on opposite sides of the other's line. Parametric form: `p0 + t·d1 = q0 + u·d2`; subtract to get `t·d1 − u·d2 = w`; taking the cross product with `d2` gives `t · cross(d1, d2) = cross(w, d2)`, and with `d1` gives `u · cross(d1, d2) = cross(w, d1)`, hence the code's `t = tn/denom` and `u = un/denom`. When `cross(d1, d2) = 0` there is no unique solution (parallel or collinear), which is why that branch must come **first**: a faulty implementation that computes `t = tn/denom` first, for the collinear overlap `(0,0)–(2,0)` and `(1,0)–(3,0)`, evaluates `0/0 = NaN`; the comparisons `0 ≤ t ≤ 1` are false, and it reports no intersection where the answer is an overlap.

Exactness: with integer-valued coordinates of magnitude at most 2^25, each difference has magnitude at most 2^26, each product of two differences at most 2^52, and a cross product (a difference of two such products) at most 2^53. Every intermediate is an integer of magnitude at most 2^53, all of which are exactly representable in binary64, so the orientation signs and the tests `tn == 0`, `tn == denom` are exact. Non-integer coordinates get no such guarantee. Recorded run: the points `(0,0)`, `(0.3, 0.9)`, `(0.1, 0.3)` are collinear in exact decimal arithmetic (0.3·0.3 = 0.9·0.1 = 0.09), but the computed cross product is −1.3877787807814457e−17, not 0, so the orientation says “not collinear.” This is the family of failure that the assigned Handmade Hero 048 segments (“walking through the top wall due to floating point precision loss”, followed by “Implementing a temporary fix”) are about: a geometric test decided by a rounded quantity. A temporary fix of that kind is not a robust predicate, and robust adaptive predicates are outside this course.

The supplied oracle in `tests/contracts.c` uses orientation-and-on-segment tests (each endpoint's `sign(cross)` and bounding-box containment) to decide whether two segments meet, integer arithmetic and a rational crossing point, and for parallel segments the set of endpoints on both segments. It shares the geometry with the implementation but not its branching structure: it never clips intervals lexicographically and never computes `u`. Learners run this supplied 6,561-pair check, explain its independence, trace a case, and add a few boundary tests. For example, `(0,0)–(2,2)` against `(0,2)–(2,0)` has opposite orientation signs for both segments; the oracle finds rational point `(1,1)`, while the implementation has `denom = −8` and `tn = un = −4`, giving `t = u = 1/2` and `(1,1)`. A useful added boundary case is a point segment `(1,1)–(1,1)` against the diagonal `(0,0)–(2,2)`, expected `SEG_POINT` at `(1,1)`; another is two separated point segments, expected `SEG_NONE`. The existing mutation record in validation.md shows several implementation mistakes detected by this independent path.

### E07.Q

The header is the interface: everything a caller may rely on, and nothing else. Include guards prevent a second inclusion in the same translation unit from redefining `SegKind` and `SegResult`. They do nothing about a function defined in a header and included from two `.c` files, which still produces a multiple-definition link error (week 2, E09). `static` gives a function internal linkage: each translation unit's copy is private, invisible to the linker, so helper names cannot collide with a caller's and cannot become accidental API; the `nm` listing above is the evidence. A library returns a status instead of printing or exiting because it does not know its caller's context: a batch processor wants counts of rejected rows, a server must not exit, a test wants to observe the failure; printing bakes one policy into all of them. The status-and-unchanged-output contract is also what lets a caller retry.

This exercise, not the earlier ones, is what later weeks depend on: week 4's generator and processor, the scalar baseline of week 5, and every distance kernel through week 35 call this interface, and the SIMD and threaded versions must produce the same results within the tolerances recorded here. To preserve when week 4 calls it: the argument order `(lat, lon, lat, lon)`, degrees, the validation ranges, the `[0, π·R]` result range, and the fact that a rejected call does not write its output.

### P01

(a) `0.1 + 0.2 == 0.3` is **false under IEC 60559 binary64** (Annex F; an implementation observation on this machine, verified by exact arithmetic in E02.Q). C11 alone does not determine it: a decimal constant may be rounded to an adjacent value (§6.4.4.2 ¶3) and `FLT_EVAL_METHOD` may make intermediate results wider. (b) `x != x` is true when `x` is NaN: **Annex F.3** (“the relational and equality operators provide IEC 60559 comparisons”), where NaN compares unordered with everything; on a C11 implementation without Annex F support NaNs need not exist. (c) False in general: `(1e16 + −1e16) + 1 = 1` but `1e16 + (−1e16 + 1) = 0`, and `(0.1 + 0.2) + 0.3 ≠ 0.1 + (0.2 + 0.3)` (measured, and by exact arithmetic). (d) False in general: `x = 1e200` gives `x * x = inf` and `sqrt(inf) = inf ≠ 1e200`; `x = 1e−200` gives `x * x = 0` and `sqrt(0) = 0 ≠ 1e−200` (both run). Without overflow or underflow I make no claim here. (e) True: **C11 §F.10.7.1 ¶2, “the returned value is exact”**, and §7.12.10.1 ¶3 defines the result as `x − ny`. The `fmod(3)` manual page describes the same computation but does *not* say it is exact, so the citation must be to the standard. Applying the Annex requires the gate (`__STDC_IEC_559__`) and subnormal support.

### P02

`0.75 = 1.1₂ × 2⁻¹`: sign 0, biased exponent 1022, fraction `.1000…` = `0x8000000000000`. `−6.5 = −110.1₂ = −1.101₂ × 2²`: sign 1, biased exponent 1025, fraction `.101000…` = `0xA000000000000`. The largest subnormal `0x000FFFFFFFFFFFFF` has exponent field 0 and fraction all ones: sign 0, exponent 0, fraction 2^52 − 1, value `(1 − 2⁻⁵²) × 2⁻¹⁰²²` = `DBL_MIN − DBL_TRUE_MIN` (E01's harness checks that stepping up by one ulp reaches `DBL_MIN`). Reconstruct `0.75`: `(−1)⁰ × (1 + 0x8000000000000/2⁵²) × 2^(1022−1023)` = `1.5 × 0.5`. For `0.1`: the exact fraction bits repeat `1001`, giving `0x9999999999999` if truncated; the next bits (`1001…`) start with 1 and are followed by more nonzero bits, which is more than half a unit, so the value rounds **up** to `0x999999999999A`, and the stored double 0.1000000000000000055511… is above one tenth. E01 prints exactly this.

### P04

Let `u`, `v` be the unit vectors, `c` the central angle. (1) `u · v = cos c` (unit length). (2) With `u = (cos φ₁ cos λ₁, cos φ₁ sin λ₁, sin φ₁)` and likewise `v`: `u · v = sin φ₁ sin φ₂ + cos φ₁ cos φ₂ cos(λ₂ − λ₁)`. (3) `hav(c) = (1 − cos c)/2`, so `hav(c) = (1 − sin φ₁ sin φ₂ − cos φ₁ cos φ₂ cos Δλ)/2`. (4) Since `hav(Δφ) = (1 − cos(φ₁ − φ₂))/2 = (1 − cos φ₁ cos φ₂ − sin φ₁ sin φ₂)/2`, subtract: `hav(c) − hav(Δφ) = cos φ₁ cos φ₂ (1 − cos Δλ)/2 = cos φ₁ cos φ₂ hav(Δλ)`. That proves the haversine form; step (3) uses only the definition of `hav` and step (2) is the nonlinear spherical-to-Cartesian coordinate map of E04, with both vectors then expressed in the same fixed basis. Chord form: `|u − v|² = |u|² + |v|² − 2u·v = 2 − 2cos c = 4 sin²(c/2) = 4 hav(c)`, so `hav(c) = |u − v|²/4`. In floating point the sum in the haversine form can round above 1 (measured above by exactly one ulp for exact antipodes with integer latitudes 8, 12, 82), and any final function defined only on `[0, 1]` or requiring `1 − a ≥ 0` then sees an argument outside its domain, so a clamp to `[0, 1]` is needed before the square root or inverse function.

### P05

Coordinates below; `d1 = p1 − p0`, `d2 = q1 − q0`, `w = q0 − p0`, `den = cross(d1, d2)`, `t = cross(w, d2)/den`, `u = cross(w, d1)/den`. (1) Proper crossing: `(0,0)–(2,2)` and `(0,2)–(2,0)`: `d1 = (2,2)`, `d2 = (2,−2)`, `w = (0,2)`, `den = −8`, `cross(w,d2) = −4`, `cross(w,d1) = −4`, so `t = u = ½`, both within `[0, 1]`; the point is `(1,1)`. (2) Parallel: `(0,0)–(2,0)` and `(0,1)–(2,1)`: `den = 2·0 − 0·2 = 0`; *before any division* test this; `cross(w, d1) = cross((0,1),(2,0)) = −2 ≠ 0`, so distinct parallel lines, no intersection. (3) Collinear overlapping: `(0,0)–(2,0)` and `(1,0)–(3,0)`: `den = 0` and `cross(w, d1) = 0`, so collinear; lexicographic lower endpoints `(0,0)`, `(1,0)` → larger is `(1,0)`; upper endpoints `(2,0)`, `(3,0)` → smaller is `(2,0)`; overlap `(1,0)–(2,0)`. (4) Touching: `(0,0)–(1,1)` and `(1,1)–(2,0)`: `d1 = (1,1)`, `d2 = (1,−1)`, `w = (1,1)`, `den = −2`, `cross(w,d2) = −2`, `t = 1`, `u = 0`; both in range; the point is the endpoint `p1 = q0 = (1,1)`. (5) Degenerate: `(1,1)–(1,1)` and `(0,0)–(2,2)`: `d1 = 0`, so `den = 0` and a naive `t = tn/den` would divide by zero; test `p0 == p1` first, then `on_segment`: `cross((2,2),(1,1)) = 0` and `(1,1)` is lexicographically between `(0,0)` and `(2,2)`: the point `(1,1)`. (6) Collinear disjoint: `(0,0)–(1,0)` and `(2,0)–(3,0)`: `den = 0`, `cross(w, d1) = 0`, collinear; larger lower endpoint `(2,0)` is lexicographically greater than smaller upper endpoint `(1,0)`, so the interval is empty and there is no intersection. All six are reproduced in the E06 driver and the harness oracle.

### P06

Rounding to six decimal places changes each coordinate by at most 5e−7 degrees (half a unit in the last place). On the reference sphere one degree of arc is `R·π/180 = 111.195080… km`, so 5e−7° is **0.0556 m** per axis in latitude, and in longitude at most that (0.0556 m · cos φ, worst at the equator). The worst-case displacement of one endpoint is √2 · 0.0556 = **0.0786 m**. The distance between two points changes by at most the sum of the two displacements (triangle inequality on the sphere), so **0.157 m worst case**: relative to a distance of 1 m that is up to **15.7 %**; to 100 m, **0.157 %**; to 10 km, **1.57e−5**, or 0.0016 %. These are worst-case bounds, not typical errors (errors are roughly uniformly distributed and often partly cancel, and the longitude component shrinks by `cos φ` away from the equator). The spacing between adjacent doubles near 180 degrees is 2^−45 = 2.84e−14 degrees, about 3.2e−9 m, which is **1.8e7 times smaller** than the text rounding.

What that implies for week 4: two different tolerances are in play. If both the program and its reference read the *same rounded text*, the remaining disagreement is arithmetic rounding and a relative tolerance around 1e−12 is defensible, as here. If the reference distances are computed from the unrounded values, the inputs already differ by up to 0.0556 m per axis and the comparison tolerance must be at least of that size, about 0.16 m absolute (1.6e−4 relative at a 1 km distance, 1.6e−5 at 10 km), no matter how accurate the double arithmetic is. Choosing a tolerance from the double spacing (about 1e−14 degrees) would be too small by seven orders of magnitude in that case. The tolerance must be derived from the dominant error source, and it should be written down together with which comparison it applies to.

### S02

[extras/stretch_antipodal.c](extras/stretch_antipodal.c). For `k = 1…12` the pair is `(0, 0)` and `(0, lon₂)` with `lon₂ = 180 − 10^−k`. Central angles are computed in radians, before scaling by `R`, so the km-to-radian division does not add its own rounding.

Prediction from the derivative of the last function. **Haversine:** `c = 2 asin(s)` with `s = cos(δ/2)` and `1 − s² = sin²(δ/2)`, so `dc/ds = 2/sin(δ/2) ≈ 4/δ` (radians). The rounding error in `s` is at most a few half-ulps below 1, that is a few units of 5.5e−17, so the predicted error is at most about `(4/δ) · 5.5e−17` per half-ulp of error in `s`, until `s` rounds to exactly 1, after which `c` is π and the error is δ itself. **Vector:** `c = atan2(y, x)` with `x = −cos δ ≈ −1` and `y = sin δ`; `dc/dy = |x|/(x² + y²) = cos δ ≈ 1`, amplification 1, so the error is just the absolute error in `y`, which comes from the argument conversion (about 1e−16), independent of δ.
