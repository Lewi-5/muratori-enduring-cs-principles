## Why this week exists

A C program becomes bytes that a processor decodes. Reading compiler output, which the course asks for from week 11 on, is much easier after decoding a real instruction set by hand and in code. The 8086 is used because its encoding is small, documented in one manual, and still visible in x86-64: the ModR/M byte, the register numbering and many opcodes survive. Week 6 starts a C decoder for a **specified subset**: `mov`, `add`, `sub` and `cmp` whose operands are registers or immediates. Memory operands and displacements (the other `mod` values of the ModR/M byte) are week 7; simulation is weeks 8–10. The C lessons are exact: reading bytes with unsigned types, extracting bit fields with shifts and masks, assembling little-endian values independently of the host's byte order, interpreting a two's-complement bit pattern without an implementation-defined conversion, and decoding a stream with bounds checks and explicit errors.

By the end, a learner should be able to split an opcode byte and a ModR/M byte into their fields and explain each field's role (`d`, `w`, `s`, `mod`, `reg`, `r/m`); name the 8- and 16-bit registers selected by a 3-bit field and explain why `ah` is not `sp`; hand-decode a byte sequence in the subset and predict its length before decoding its operands; write a decoder whose output is a function of the bytes alone, which rejects anything outside the subset with a stated status and offset; and explain why decoding is a function from bytes to text but assembling is not its inverse (one text can have several encodings).

Do not add later-week topics: memory operands, effective-address calculation, displacements or segment prefixes (week 7), a public decoder library API or shared library (week 7), jumps and loops beyond the optional stretch exercise (week 9), register or flag simulation (weeks 8–9), cycle estimates (week 11), or x86-64 decoding beyond the one comparison in P06. Handwritten assembly is not required this week; the course's short assembly probe is week 11.

## Constraints carried forward from earlier reviews

The week-2 and week-4 lessons still apply: verify every claim; state overflow contracts; state explicit limits (input size, buffer sizes, accepted values); validate before committing outputs; sequence side effects; give learners typed, warning-clean TODO functions and supplied drivers; mutation-test the harness and classify survivors. Fixed expected outputs are legitimate here, as they were for week 4's format: the instruction encoding is fully specified and platform-independent, so the decoder's text is compared exactly.

The [week-3 review](../week-03/actions.md) found defects that a passing suite had not revealed. Its five actions are generalized here and checked in the acceptance section:

- **Derive results from the original data, not from a lossy intermediate (A1).** Immediate values are rebuilt from the original bytes and the `w` and `s` bits; the instruction's printed text is produced from the decoded structure, never by re-parsing earlier text; the reported error offset is the offset of the instruction's first byte in the original stream. Tests include inputs that expose a shortcut: an 8-bit immediate `0x80`–`0xFF` with `s = 1` (sign extension changes the value) and with `w = 0` (it does not).
- **Check every proof step against a counterexample search (A2).** The plan's structural claims — for example “an instruction's length is known once the bytes that select its form have been read” — are checked exhaustively over the subset's two-byte prefixes before any explanation relies on them. For example, “an instruction's length is a function of its first byte” holds for the instructions this subset *accepts*, but the *status* is not a function of the first byte (`0x80`–`0x83` and `0x88`–`0x8B` need the ModR/M byte to decide support), and the length claim fails as soon as memory modes are admitted (in week 7, `mod = 01` and `10` add displacement bytes). The answer key states exactly how far the claim holds, with the exhaustive check and the week-7 counterexample. A test illustrates a proof; it does not replace one.
- **Keep exact claims exact (A3).** Decoding is integer work and is compared exactly. Where the C standard makes a conversion implementation-defined (a `uint16_t` value above `INT16_MAX` converted to `int16_t`, C11 §6.3.1.3 ¶3) or leaves a result implementation-defined (right shift of a negative value, §6.5.7 ¶5), the reference code avoids it; the answer key names the clause rather than relying on what one compiler does.
- **Use precise terms and demonstrate them (A4).** Distinguish an *opcode* (the bits that select an operation and form) from an *instruction* (the whole encoded sequence); *decoding* (bytes to a structured instruction), *disassembling* (decoding plus printing text) and *assembling* (text to bytes, not unique); the 8086's architectural registers from x86-64's; and the ISA model from any microarchitecture (week 12). Each distinction is demonstrated with a concrete byte sequence, as week 3's revised E04.Q demonstrates a basis change instead of naming it.
- **Keep the workload credible and the uncertainty explicit (A5).** The exhaustive oracle and the `objdump` cross-check are **supplied**. The learner explains why each is independent of their decoder, traces one case through the oracle, and adds a small number of purposeful test cases; they do not write a second decoder or an encoder. The estimate below is unpiloted; the validation record says so and includes the pilot procedure.

## The course subset and output format (definitions used by all exercises)

- **Instructions in the subset** (all others are `DEC_UNSUPPORTED_OPCODE`):
  - `mov` register to register: `100010dw` then ModR/M (`0x88`–`0x8B`).
  - `mov` immediate to register: `1011wrrr` then an 8-bit (`w = 0`) or 16-bit (`w = 1`) immediate (`0xB0`–`0xBF`).
  - `add`, `sub`, `cmp` register with register: `00ooo0dw` then ModR/M, where `ooo` is `000` (`add`, `0x00`–`0x03`), `101` (`sub`, `0x28`–`0x2B`) or `111` (`cmp`, `0x38`–`0x3B`).
  - `add`, `sub`, `cmp` immediate to register: `100000sw` then ModR/M whose `reg` field is `000`, `101` or `111`, then the immediate: 16 bits when `s:w = 01`, 8 bits otherwise, sign-extended to 16 bits when `s:w = 11` (`0x80`, `0x81`, `0x83`).
  - `add`, `sub`, `cmp` immediate to accumulator: `00ooo10w` then an 8- or 16-bit immediate (`0x04`/`0x05`, `0x2C`/`0x2D`, `0x3C`/`0x3D`).
- **Outside the subset this week, with explicit statuses:** a ModR/M `mod` other than `11` in a recognized form is `DEC_UNSUPPORTED_MODE` (week 7); a `reg` field in `0x80`–`0x83` other than `000`, `101` or `111` (`or`, `adc`, `sbb`, `and`, `xor`) is `DEC_UNSUPPORTED_OPERATION`; opcode `0x82` (`s:w = 10`) is `DEC_UNSUPPORTED_OPCODE`. `objdump` decodes `82 c1 05` as `add cl,0x5` (checked on the reference machine), so the course's rejection is a *scope decision*, not a claim about the hardware; the implementing agent records what the 1979 manual says about this encoding and the answer key explains the decision.
- **Status order** when decoding one instruction: read the first byte (none: `DEC_TRUNCATED`); if its opcode is not in the subset, `DEC_UNSUPPORTED_OPCODE`; if the form needs a ModR/M byte and none remains, `DEC_TRUNCATED`; then `DEC_UNSUPPORTED_MODE`, then `DEC_UNSUPPORTED_OPERATION`; finally, if the immediate's bytes are not all present, `DEC_TRUNCATED`. Each failure reports the offset of the instruction's first byte. `DEC_OUTPUT_TOO_SMALL` and `DEC_INVALID_ARGUMENT` are stream/format API failures, not byte-encoding classifications; file I/O and size errors are command-level errors rather than decoder statuses.
- **Canonical text:** lowercase mnemonic, one space, destination, `", "`, source: `mov cx, bx`, `add si, -2`, `cmp al, 12`. Registers: `w = 0` → `al cl dl bl ah ch dh bh`; `w = 1` → `ax cx dx bx sp bp si di` (field values 0–7). The `d` bit selects which of `reg` and `r/m` is the destination (`d = 1`: `reg` is the destination). Immediates are printed in signed decimal **as a value of the operand's width**: the 16-bit pattern `0xFFF4` prints as `-12`, the 8-bit pattern `0xF4` in `mov cl, …` prints as `-12`, and an 8-bit immediate sign-extended by `s = 1` prints its extended value. The text contains no size keyword because every operand in the subset is a register whose width fixes the size (week 7 adds `byte` and `word`).
- **Stream output:** the first line is `bits 16`, then one instruction per line, each ending with `\n`. The output is NASM-compatible so that learners who have an assembler can reassemble it; the course does not require one.
