### E01.C

[ex01.c](src/ex01.c). `lcg_next` performs `*state = *state * A + C` in `uint64_t` and returns `(uint32_t)(*state >> 32)`; the advance happens *before* the output, so the first output for seed 0 is the high half of `C` itself (`14057B7E`). Unsigned arithmetic wraps modulo 2^64 by definition (C11 §6.2.5¶9), so the function is a pure function of the state on every conforming implementation. `lcg_below` rejects NULL pointers and `bound == 0` before touching anything, then computes `threshold = (uint32_t)(0u - bound) % bound`, which is `2^32 mod bound` (unsigned negation is `2^32 − bound`), and redraws while `r < threshold`. What is left, `[threshold, 2^32)`, contains `2^32 − threshold` values, an exact multiple of `bound`, so each residue occurs equally often. Bound 1 has threshold 0, accepts the first draw and yields 0 — but it *consumes* that draw, which the tests check through the state that follows. The tests read the oracle's first 1,000 outputs for seeds 0, 1 and `UINT64_MAX`, then 200 `lcg_below` results and the final state for five bounds and three seeds; the final state proves the same number of raw draws was consumed including rejected ones. A second oracle file, built by *inverting* the recurrence (`s_prev = (s_next − C)·A⁻¹ mod 2^64`, possible because `A` is odd), places the next raw output exactly on `threshold − 1`, `threshold` and `threshold + 1` for six bounds: this is what separates `r < threshold` from `r <= threshold` (a mutant that rejects one extra value differs from the correct code once in 2^32 draws, so random sampling cannot see it). Driver output: `seed=0 first=14057B7E,1A08EE11,9AF67822` and `bound7=4,3,5,5,5,0,1,5,4,5` (oracle; `bc` reproduces the first three outputs, see the validation record). Faulty approaches, each killed by a mutant test: omitting the loop (`return r % bound`, bias), `r <= threshold`, returning the low 32 bits, and emitting the output before advancing the state.

### E01.Q

**Recurrence and wraparound.** `s' = a s + c (mod 2^64)`. In C, `uint64_t` arithmetic is reduced modulo 2^64 (C11 §6.2.5¶9: “a computation involving unsigned operands can never overflow”); signed overflow is an exceptional condition and the behavior is undefined (§6.5¶5), so a compiler may assume it never happens. Using a signed state would make the generator's output depend on the optimizer. **Hull–Dobell.** A generator `s' = a s + c mod m` has period `m` (visits every state) iff (1) `gcd(c, m) = 1`, (2) `a − 1` is divisible by every prime factor of `m`, and (3) by 4 if 4 divides `m`. For `m = 2^64` the only prime factor is 2 and 4 divides `m`, so the conditions reduce to: `c` is odd and `a ≡ 1 (mod 4)`. `c = 1442695040888963407` is odd; `a − 1 = 6364136223846793004` ends in `04`, which is divisible by 4. Both are `_Static_assert`s in the reference and asserted in the oracle. Full period means all 2^64 states occur once per cycle, so two different seeds are two positions on the *same* cycle. **High bits.** In a power-of-two modulus LCG bit *k* of the state has period at most 2^(k+1): bit 0 alternates, bit 1 has period 4. Taking the high 32 bits uses the longest-period bits; N1570 even warns (footnote 295 to §7.22.2.2) that some `rand` implementations have “distressingly non-random low-order bits”. **`rand()`.** C11 promises only that the same seed repeats the sequence *on that implementation*; the algorithm, the range beyond `RAND_MAX ≥ 32767` and the quality are unspecified, so the bytes of a dataset would change with the C library (P01). **Modulo bias** is worked in P02: for bound 3,000,000,000 the residues below 1,294,967,296 occur twice as often as the rest; *measured* over 2·10^7 draws, `r % bound` falls below 1,294,967,296 with frequency 0.6029 (exact 0.6030) whereas rejection sampling gives 0.4315 (exact 0.4317). **Termination.** Let `T = 2^32 mod bound`. Since `T < bound` and `T ≤ 2^32 − bound`, `T < 2^31`, so at least half of all 32-bit values are accepted. The state cycles through all 2^64 states, so at least `2^32 (2^32 − T) > 2^63` of them are accepted; a run of rejected draws therefore cannot exceed 2^63, which is finite but useless. The useful statement is probabilistic: modeling the high bits of consecutive states as independent (an approximation, not a proof), the number of draws is geometric with mean `1 / (1 − T/2^32)`: 1.4317 for bound 3e9 and below 2 for every bound. *Measured* over 10^8 draws each: rejected fraction 0.301508 and 0.301533 for two seeds (exact 0.301508) with longest rejected runs of 16, and 0.500075 for the worst bound `2^31 + 1` with a longest run of 23, consistent with `P(run ≥ k) = pᵏ` (expected longest ≈ ln(10^8 (1−p)) / ln(1/p) ≈ 15 for p = 0.3015). **Weak.** An LCG has a lattice structure (points `(s_i, s_{i+1})` lie on few lines), the state equals the output history, and consecutive draws are strongly related; it is fine for this course's reproducible data and unfit for entropy tests, which is why week 47 replaces it.

### E02.C

[ex02.c](src/ex02.c). `format_udeg` first rejects NULL and any `limit` outside {90000000, 180000000}, then widens `value` to `int64_t` *before* taking the magnitude, so `INT32_MIN` (magnitude 2^31) is representable and no `int32_t` is ever negated. It rejects `|value| > limit`, builds the text in a local buffer (sign, integer part by repeated division, `.`, six digits from a descending power of ten) and only if `out_size ≥ length + 1` copies it with the NUL. Building in a temporary is what guarantees “output untouched on rejection”. `format_record` writes the decimal identifier (a `do … while` so 0 prints), `,`, the latitude field (limit 90000000), `,`, the longitude field (limit 180000000) and `\n` into a temporary and copies it if it fits. Edge cases the tests hit: `0 → 0.000000`, `-1 → -0.000001`, `999999 → 0.999999`, `1000000 → 1.000000`, `-500000 → -0.500000`, `±limit` accepted and `±(limit + 1)` rejected, `INT32_MIN`/`INT32_MAX`/every invalid limit rejected, every buffer size from 0 to the exact length (`-180.000000` needs 12 bytes, a 44-character record needs 45), and all 3,000,001 values from −1,500,000 to 1,500,000 against a harness formulation built from `snprintf`, `/` and `%` on `int64_t` — a different formulation of the same integer arithmetic, plus the Python oracle for the driver's records. Faulty variants (each a killed mutant): losing the sign of values in (−1, 0), not zero-padding the fraction (`0.5` instead of `0.000005`), an off-by-one buffer test, writing part of the output before failing.

### E02.Q

**Fixed point.** A microdegree count is an integer; a coordinate `x.dddddd` *is* that integer scaled by 10^6. Formatting an integer with integer arithmetic is exact and has no rounding step, so the file's text and the integers a program holds correspond one-to-one; the six-decimal restriction is a statement about the *grammar*, not an approximation. **Why not `%f`.** `printf("%.6f", d)` (a) formats a *binary* value, so the text depends on the correctly rounded conversion of a double that is not the decimal number (`0.1` is stored as 0.1000000000000000055…), (b) uses the locale's decimal-point character (C11 §7.11: the characters used by the numeric conversion functions are locale-dependent; the default “C” locale gives `.`, but a program that calls `setlocale(LC_ALL, "")` may not; the `de_DE` locale is not installed on the reference machine, so this was not reproduced here and rests on the standard). **Sign around zero.** For `value = -1` the integer quotient `value / 1000000` is 0 (truncation toward zero in C99/C11), so a sign taken from the quotient disappears. *Measured* on the reference build: `printf("%d.%06d", v / 1000000, abs(v % 1000000))` prints `0.000001` for −1 and `0.500000` for −500000, silently changing the sign; with the raw remainder instead it prints `0.-00001` and `0.-500000`. The fix is to test `value < 0` once, print the sign, and format the magnitude. **INT32_MIN.** `-INT32_MIN` does not fit in `int32_t`: an exceptional condition, undefined behavior (C11 §6.5¶5). Computing the magnitude in `int64_t` avoids it, and the domain is `|value| ≤ 180000000`, so `INT32_MIN` is rejected by range, not by luck. **Lengths.** Latitude: sign (1) + at most 2 integer digits + `.` + 6 = 10; longitude: 1 + 3 + 1 + 6 = 11, so 12 bytes with the NUL. Record: at most 20 (a `UINT64_MAX` identifier) + 1 + 10 + 1 + 11 + 1 (newline) = 44 characters, 45 bytes.

### E03.C

[ex03.c](src/ex03.c). `generate_csv` rejects NULL and `count > GEOLAB_MAX_ROWS` before writing anything (the test checks that `ftell` is 0 afterwards), writes the header with `fputs`, and for each row draws latitude into a local `r`, forms `lat_udeg`, *then* draws longitude — two statements — formats the record and `fputs` it. It returns `ferror(out) == 0` at the end, so an error surfaced only by a later flush is not confused with success. `write_csv_file` validates the arguments, opens with `"wb"`, calls `generate_csv`, `fflush`, then `fclose` — exactly once, whatever happened — and only `if (!ok)` calls `remove(path)`. The failed-`fopen` path returns immediately: the path may name something this call did not create, and `remove` on an *empty directory* deletes it (POSIX `remove` falls back to `rmdir`), so calling it there would be a bug; the test opens the test directory itself as the path and checks the directory survives and `remove` was never called. The tests compare byte for byte with oracle files for (seed 1, 1,000 rows), (0, 1) and (`UINT64_MAX`, 257 rows), check the structure of 1,000 generated rows with an independent grammar checker, and use four kinds of failure: a stream opened for reading (every write fails), a 100-byte `fmemopen` stream (fails partway through the rows, which is what makes the row-loop checks observable), an injected `fclose` failure, and an injected `fflush` failure; after each `write_csv_file` failure the file is gone. The driver contract is checked from Python: each option once in any order, counts 0…cap, seeds up to `UINT64_MAX`, and 16 malformed command lines (missing, duplicate, unknown option, `-1`, ` 5`, `+1`, `1.5`, empty, 2^64, count above the cap, dangling option, stray argument) all fail with a nonzero exit and **no file created**. The recorded digests are `3b13098d…145da` for (1, 1000) and `31334919…be440` for (11400714819323198485, 100000); they are hard-coded in the oracle and reproduced by GCC and Clang at `-O0` and `-O2`, so the files are byte-identical across all four builds. **Redundancy note (from mutation testing):** the individual checks of `fputs`'s result and of `ferror` are each sufficient to detect a failure that is still visible on the stream, so removing only one of them is an *equivalent mutant*; removing both is caught by the `fmemopen` test.

### E03.Q

**Determinism argument.** The bytes are a function of `(seed, count)` because (1) every arithmetic step is on unsigned integers, whose results the standard defines (§6.2.5¶9); (2) the order of the draws is fixed by statement order, not by the unspecified order of argument evaluation (§6.5.2.2¶10), and the number of draws consumed by rejection sampling is itself a function of the state; (3) the text is produced from integers by a fixed algorithm — no floating point, no locale; (4) the file is opened in binary mode, so no newline translation occurs on platforms that have one. Nothing in the pipeline depends on the compiler, optimization level, endianness or `sizeof(int)`; the recorded SHA-256 digests match across GCC/Clang at `-O0`/`-O2`, and the *measured* file for seed 1 and 1,000 rows has 25,253 bytes. **Failure order.** Check each write (a failing `fputs` returns EOF), check `ferror`, `fflush`, then `fclose` exactly once — a buffered stream can report a disk-full error only at flush or close, so an unchecked `fclose` can return success for a truncated file — and only then, if anything failed, `remove` the partial file. Which checks a failure can hide behind: an error indicator set by an early write remains visible to `ferror` later, so the per-write checks and the final `ferror` overlap; `fclose` can fail even when every write succeeded, and that is the one that is never redundant. **Why not `remove` after a failed open.** The file was never created by this call: the path may be a directory or someone else's file. **Existing file.** `fopen(path, "wb")` truncates first, so if generation fails the previous contents of `path` are already gone and the function removes the partial file: on failure the old file is lost. Writing to a temporary name and `rename`-ing on success would avoid that; it is outside this week, and it is stated in the source. **Uniform degrees.** Latitude uniform on `[−90, 90]` gives a density constant in φ, but the area element of the sphere is proportional to `cos φ dφ dλ`, so the point density per unit area is proportional to `1/cos φ`, growing toward the poles. *Measured* with seed 1 and 2·10^5 points: 33.4% have `|lat| > 60°` (exactly 1/3 for uniform degrees) whereas only `1 − sin 60° = 13.4%` of the sphere's area lies there. **Row cap.** The cap bounds the file (about 25 MB at 10^6 rows of 25 bytes) and, because the loader allocates 24 bytes per row on the reference platform, the array (24 MB); it makes “rows fit in memory” a property of the format rather than a hope.

### E04.C

[ex04.c](src/ex04.c). `parse_record` first rejects a NULL input line or output pointer with `PARSE_INVALID_ARGUMENT` without writing, then counts the commas once (`PARSE_EMPTY` for an empty line first; `PARSE_FIELD_COUNT` unless there are exactly two), then examines the three fields in the fixed order identifier, latitude grammar, latitude range, longitude grammar, longitude range, so each line has exactly one first failing status. `parse_id` accepts 1–20 digits, no leading zero unless the field is the single character `0`, and accumulates with the guard `v > (UINT64_MAX − d) / 10`. `parse_udeg` takes an optional `-`, counts the integer digits (bounded by 2 or 3 *before* accumulating, so the value is at most 999,999,999 and cannot overflow an `int64_t`), requires `.` and exactly six digits, rejects `-0.000000`, and returns range only after the grammar is valid — `100.000000` in latitude is a grammar error (three integer digits) and `91.000000` a range error. The result is `(double)micro / 1000000.0`, negated for a leading minus; `*out` is written only at the very end. The tests check 48 hand-listed lines, then **8,510 lines from the oracle** (1,248 valid) built from boundary values, identifiers around 2^64, and every single-character deletion, insertion and replacement of twelve base lines over an alphabet that includes `+`, space, `e`, `x`, `\r` and a non-ASCII byte: the C status must equal the Python regular-expression classifier's, `*out` must be unchanged on every failure, and for every valid line the doubles must equal `(double)micro / 1e6` and, under the Annex F gate, `strtod` of the field text. Expected status of each line in the driver: `1,0.000000,0.000000` OK; the `UINT64_MAX` line OK; `7,-33.868800,151.209300` OK; `01,…` BAD_ID; `5,91.000000,0.000000` LAT_RANGE; `5,1.5,2.000000` BAD_LAT; `3,0.000000` FIELD_COUNT; `9,-0.000000,0.000000` BAD_LAT; `10,45.000000,181.000000` LON_RANGE; the 2^64 identifier BAD_ID; the empty line EMPTY. Faulty variants killed by mutants: leading zeros accepted, `-0.000000` accepted, product-only overflow check, a latitude limit of 91, three-digit latitudes, `commas < 2`, `micro * 1e-6` instead of division, writing `*out` before validation, a longitude limit of 181, range errors reported as grammar errors, five fraction digits accepted. One mutant survives by design: dropping the `n > 20` length check is equivalent, because a 21-digit number without a leading zero always exceeds `UINT64_MAX` and the overflow guard rejects it anyway (the length check is a cheap early exit).

### E04.Q

**Canonical form.** For a dataset, *one* spelling per value means equality of text is equality of value, files can be compared and hashed as bytes, and a parser has a small, testable state space. A lenient grammar (`+1`, `1.50`, `.5`, `1e2`, spaces) accepts inputs the generator never writes and turns typos into silently wrong coordinates. **Ordered error classes.** With a fixed order (empty, count, id, lat grammar, lat range, lon grammar, lon range) a line with two defects has one reported status, so diagnostics are deterministic and testable, and the oracle can decide the expected status without knowing the implementation. **The overflow guard.** `v * 10 + d` fits iff `v ≤ (UINT64_MAX − d) / 10` (integer division), and both the multiplication and the addition can overflow. A guard that only tests the product (`v > UINT64_MAX / 10`) admits `v = 1844674407370955161` (which equals `UINT64_MAX / 10`) with any digit: for `d ≥ 6` the true value exceeds `UINT64_MAX = 18446744073709551615`. *Measured:* `1844674407370955161 * 10 + 6` wraps to 0, so the identifier `18446744073709551616` would be silently accepted as identifier 0. The test list contains that identifier, and 18446744073709551615, the largest valid one. **Why not `strtod`.** It accepts what the grammar forbids — *measured* on the reference build: `nan`, `inf`, `0x1p3` (hexadecimal float), `" 1.5"` (leading space), `1e2`, `+1.5`, `.5`, `5.` and `-0.000000` all convert, consuming the whole text — and its decimal point follows the locale (§7.11). **Why not `isdigit` on `char`.** `isdigit`'s argument must be representable as `unsigned char` or equal `EOF` (§7.4¶1); a plain `char` holding a negative value other than −1 (for instance a UTF-8 byte) is undefined behavior. Comparing `c >= '0' && c <= '9'` is defined for every `char` and the digits are contiguous in every execution character set (§5.2.1¶3). **Exactness of the conversion.** Let `m` be the integer of microdegrees, at most 180,000,000 < 2^53. Then `(double)m` is exact, `1000000.0` is exact (10^6 < 2^53), and IEEE division rounds the true quotient `m / 10^6` to the nearest double (Annex F: division is correctly rounded in the default rounding mode). Annex F.5¶2 states that conversion between an IEC 60559 format and decimal with `DECIMAL_DIG` or fewer significant digits is correctly rounded, and the text has at most 9 significant digits, so `strtod` returns the nearest double to the *same rational number*. Two correctly rounded results of the same real number are equal, which is why the test compares them with `==`; the negative case follows because rounding to nearest is symmetric. Preconditions: an IEC 60559 implementation (`__STDC_IEC_559__`), round-to-nearest, `double` = binary64; the check is skipped otherwise and the forced-skip build exercises that path. (The plan cited “Annex F.5”; the title in N1570 is “Binary-decimal conversion” and the operative sentence is ¶2.)

### E05.C

[ex05.c](src/ex05.c). One `fgetc` loop with an `int c`. `EOF` is examined first: `ferror(f)` means `PARSE_IO_ERROR`; otherwise a nonempty partial line is processed as the final line, and a zero-byte file is `PARSE_MISSING_HEADER`. A `'\n'` completes a line, which `handle_line` treats as the header (line 1, exact match) or a row (`parse_record`, then `append_row`); a NUL byte is `PARSE_NUL_BYTE` on the spot; the 128th non-newline character of a line is `PARSE_LINE_TOO_LONG` (the buffer holds 127 characters plus the terminator added by `handle_line`). `append_row` implements growth: at the cap a further *valid* row is `PARSE_TOO_MANY_ROWS`; otherwise capacity starts at `min(1024, GEOLAB_MAX_ROWS)` and becomes `cap > max/2 ? max : cap*2` (so the doubling cannot overflow), the byte count is checked against `SIZE_MAX / sizeof(GeoPoint)`, `malloc` is used for the first block and `realloc` — assigned to a temporary — for the rest. Every exit funnels through one place that calls `fclose` (its failure after an otherwise successful parse is `PARSE_IO_ERROR`, line 0) and, on failure, `free(rows)`, fills `*err`, and leaves `*points` and `*count` alone. The tests use 22 byte-exact fixtures — each with its expected line and status (e.g. `bad_id.csv` line 4; `blank_middle.csv` line 3; `blank_last.csv` line 4; `crlf.csv` `PARSE_BAD_HEADER` line 1 because the CR belongs to the header line; `line_127.csv` is a 127-character line accepted by the reader and rejected as `PARSE_BAD_ID`, `line_128.csv` is `PARSE_LINE_TOO_LONG`; `high_byte.csv` has a `0xFF` byte and must be `PARSE_BAD_ID` at line 3), a 3,000-row file written by the oracle with the companion integers for every row, and instrumented runs: the wrapper records every allocation size, so 3,000 rows cost one `malloc(1024·24)` and two `realloc`s of `2048·24` and `4096·24` bytes on the reference platform; builds with `GEOLAB_MAX_ROWS` lowered to 8 and to 1500 verify the clamped first allocation (8 elements), the clamped doubling (1024 then 1500, not 2048), a file of exactly the cap accepted with and without a final newline, and one row more rejected as `PARSE_TOO_MANY_ROWS` at line cap + 2. Failure injection fails the first allocation, the first and second growth (line numbers 1026 and 2050), `fclose` (with a good file, and with a bad file, where the parse error must win), and the 25th and 30th `fgetc`; after every failure the harness asserts `live_blocks == 0`, the outputs unchanged, and the file closed exactly once. Under AddressSanitizer/LeakSanitizer no error path leaks. One mutant survives on purpose: deleting the `SIZE_MAX / sizeof(GeoPoint)` check — no file can drive capacity that high on a 64-bit target with the course cap, so the check is unreachable by any test; it is a contract for a raised cap or a 32-bit `size_t`, argued by inspection.

### E05.Q

**Bounded reading.** With a `GEOLAB_MAX_LINE + 1` byte buffer and a length counter the reader never writes past the array and never lets input length decide memory. `fgets(buf, 128, f)` would also be memory-safe, but *measured*, a 200-character line comes back as two “lines” of 127 and 74 characters; the second piece would be parsed as a record and the first as another, so a malformed 200-character line could yield two different errors or, worse, look valid; the reader must instead notice that the newline is missing and reject the line. **EOF versus `ferror`.** `fgetc` returns `EOF` both at the end of the file and on a read error; only `ferror` (or `feof`) tells them apart, and treating an I/O error as end-of-file loads a silently truncated dataset. **`int`, not `char`.** `fgetc` returns an `unsigned char` value converted to `int` (0…255) or `EOF` (negative). Storing it in a `char` that is signed (it is, on the reference platform — *measured*: `(char)0xFF == EOF` is 1) makes the byte 0xFF indistinguishable from `EOF`, so a valid file with such a byte would end early; the `high_byte.csv` fixture catches this. **NUL and CR.** A NUL cannot live inside a C string, so `strlen`-based parsing would see a shortened line and might *accept* a corrupt one; it must be detected while reading. A `\r` (CRLF files from other tools) is not part of the grammar, so it must fail loudly rather than be trimmed; through the grammar it fails as `PARSE_BAD_LON` for a row and `PARSE_BAD_HEADER` for the header. **Ownership.** Before the array exists nothing needs freeing; after, every failure must `free` it and every path must `fclose` the file once; on success the array belongs to the caller. A single exit block makes the cleanup order obvious and testable. **The `realloc` idiom.** `p = realloc(p, n)` overwrites the only pointer to the old block with NULL when `realloc` fails, leaking the block (C11 §7.22.3.5: on failure the old object is not deallocated and its value is unchanged, so it is still valid and must be released); the fix is `tmp = realloc(p, n); if (!tmp) { … free(p) … }`. The instrumented tests fail the second allocation and require zero live blocks. **Checked growth.** The doubling cannot wrap because it happens only when `cap ≤ max/2`; the byte count `cap * sizeof(GeoPoint)` is checked against `SIZE_MAX` before every call, because an unchecked product can wrap to a small number and make `realloc` succeed with a block too small for the writes that follow. **Line numbers.** The header is line 1, each `\n` increments the counter, an error at a line reports that line, the final unterminated line counts as a line, an empty file reports line 1, and an open failure or a failing `fclose` report 0 because no line is responsible.

### E06.C

[ex06.c](src/ex06.c). `process_points` validates in this order, writing nothing: `out` non-NULL; `points` non-NULL when `count > 0`; center finite and in range; radius finite and in `[0, 100000]`; every point finite and in range (`isfinite` and comparisons; a NaN fails every comparison, so `NaN` latitudes are rejected without a special case). Only then does it loop, calling the haversine (`a = sin²(Δφ/2) + cos φ₁ cos φ₂ sin²(Δλ/2)`, clamped to `[0, 1]`, distance `2·asin(√a)·R` with R = 6371.0088 km, a model constant), counting `d <= radius_km`, accumulating `sum += d` left to right, tracking min and max from the first point, and assigns `*out` once at the end. An empty dataset returns zeros (min and max are meaningless, so they are defined as 0). The built-in dataset: equator longitudes −2…3 and 10, both poles, `(0,±180)` and `(45,45)`; with radius `R · rad(2.5)` exactly the five points at −2, −1, 0, 1, 2 degrees are inside (the point at 3° is 0.5° beyond the boundary), so `within=5`. Analytic expectations: an equator point at longitude λ is `R·rad(|λ|)`; a pole is `R·π/2` from the equator; `(0, ±180)` is `R·π`; `(45, 45)` has `cos c = cos 45° cos 45° = 1/2`, so `c = π/3`. The sum is `R·(rad(2+1+0+1+2+3+10) + 2·π/2 + 2π + π/3) = R·(rad(19) + 3π + π/3)`, `min = 0` (the center point) and `max = π R`. *Measured driver output:* `points=12 within=5 sum_km=68829.754665 min_km=0.000000 max_km=20015.114442` and `reference_max_abs_diff_km=1.819e-12 within_equal=1`. The 10,000-point differential test uses the harness's own LCG for the points and the supplied unit-vector distance (`atan2(|u × v|, u · v)` with plain `sin`/`cos`, accumulated in a `long double`) as the reference, for four centers (including a pole and a point beside the antimeridian) and five radii; `within` must be equal, `sum_km` within 2·10⁻¹² relative, `min_km`/`max_km` within 10⁻¹¹ relative with a 10⁻⁹ km floor. Radii were checked to keep every point at least 10⁻⁶ km from the boundary, because a point that close could legitimately land on either side under two formulas.

### E06.Q

**Trust in a reference.** A reference is trusted because it is *simple* enough to inspect, written by a *different method* from the code it judges (here the unit-vector angle versus the haversine), and checked against an *independent oracle* (the analytic values for the built-in dataset; the LCG and grammar oracle for the data). Speed plays no part. **What differential testing cannot catch.** Two implementations that share a constant, a model or a misconception agree and are both wrong: both use R = 6371.0088 km and the spherical model, so the test says nothing about geodesic accuracy; both would fail the same way if latitude and longitude were swapped in the input convention; and a reference built from the same formula would not be independent at all. What it *does* catch is a slip in one implementation — wrong radian conversion, a boundary mistake, a bad accumulation — which is why the tests include such slips as mutants (all killed). **Inclusive boundary.** `d <= radius` on doubles is exactly as reliable as the computation of `d`: two mathematically equal quantities computed by different formulas differ in the last bit, so a point “exactly at” the radius can be inside for one formula and outside for another. The test therefore avoids asking two implementations to agree at the boundary; it checks that the *same* code is consistent with itself: process one point to obtain its distance `d`, then use `d` as the radius (`within = 1`) and `nextafter(d, 0)` (`within = 0`). **Accumulation and the sum tolerance.** The sum is left to right in `double`; for `n` positive terms the rounding error is at most `γ_{n−1} S` with `γ_k = k u / (1 − k u)` and `u = 2^-53`; for n = 10⁴ that is 1.11·10⁻¹² relative. Add the disagreement of individual distances: *measured*, the largest per-point difference between haversine and the reference on this corpus is 3.3·10⁻⁹ km, at the point (−89.98°, 21.24°) seen from the north pole (nearly antipodal — a week-3 effect: the haversine's `asin` argument is near 1, where it amplifies a rounding by `1/√(1−a)`; a `long double` reference shows the *reference* is accurate to 5.5·10⁻¹² km there), and the smallest reference sum is 9.96·10⁷ km, so that contributes at most `10⁴ · 3.3·10⁻⁹ / 9.96·10⁷ = 3.3·10⁻¹³` relative. The tolerance 2·10⁻¹² covers both; *measured* the actual sum difference is at most 3.1·10⁻¹⁵ (0.28% of the `(n−1)u` bound, as expected since rounding errors are mostly random and cancel). **Analytic derivation:** see E06.C.

### E07.C

[ex07.c](src/ex07.c). `sum_naive` is a loop. `sum_pairwise` recurses: a block of at most 8 elements is summed naively from `0.0`, a larger block is split at `n / 2` and the two halves are added; the recursion depth is `⌈log2(n/8)⌉` (17 for 10⁶). `sum_neumaier` keeps `sum` and a running correction `c`: after `t = sum + x` it adds to `c` the exact rounding error of that addition, computed as `(sum − t) + x` if `|sum| ≥ |x|` and `(x − t) + sum` otherwise (the smaller operand's low bits are the ones lost, and subtracting `t` from the larger operand first is exact), and returns `sum + c`. `grid_accumulated` and `grid_explicit` reject `n > 2^24`, non-finite `start` or `step` (even when `n = 0`), a NULL `out` with `n > 0`, and a non-finite final element, *before writing*: the accumulated version runs the whole loop once without storing to learn the final value, the explicit version computes `start + (n−1)·step` directly; a monotone grid has its extremes at its ends, and rounding cannot make it non-monotone, so a finite last element means all are finite. The accumulated writer does not take an extra step after storing the final requested value. The bound `2^24 = 16,777,216` is the largest count for which every index is exactly representable even as a `float`; a `double` index is exact far beyond that. *Measured driver output* (all four builds; Python's re-implementation of the same operations reproduces every printed digit, which is the independent check): `cancel` naive 1, pairwise 1, Neumaier 2 (exact 2); `tenths` naive 100000.00000133288, pairwise 100000, Neumaier 100000 (exact 100000); `ramp` all 500000500000; `hashed` naive 71428826199.142868, pairwise 71428826199.142868, Neumaier 71428826199.142853 (exact 71428826199.142853, `math.fsum`); `grid n=1000001 accumulated_max_rel_err=1.332884e-11 explicit_max_rel_err=2.220432e-16`. Tests: exactness on integers for every prefix length around the block boundaries (0…40) and for `ramp` (every partial sum is an integer below 2^53); Neumaier equals 2 on `cancel` and on its three reorderings (the reordered inputs are what expose a compensation that only handles one operand order); Neumaier exactly recovers `2^53 + 1000` where a plain sum stays at `2^53`; IEEE behavior for overflow and non-finite input; rejections leave the array untouched; the error bounds against `math.fsum` (below); and the grid bounds (E07.Q). Faulty variants killed by mutants: compensation without the branch, a dropped correction, pairwise with a huge block or a linear split, an explicit grid that accumulates.

### E07.Q

**Accumulation versus explicit calculation.** In Handmade Hero 146 (42:07–56:04) the sample position advanced by `position += step` every sample; each addition rounds, and the rounding errors are correlated (the same `step` is added to a growing value), so the position drifts; computing `position = start + i * step` from the index has at most two roundings whatever `i` is. *Measured* here: adding `0.1` a million times gives a maximum relative error of 1.33·10⁻¹¹ against the exact `i/10` (120,055 `u`), while `start + i * step` gives at most 1.48·10⁻¹⁶ (1.33 `u`). **Error bounds** (`u = 2^-53`, `γ_k = k u / (1 − k u)`, all for the computed sum against the exact sum of the given doubles): naive `|E| ≤ γ_{n−1} Σ|xᵢ|` (Higham §4.2); pairwise with 8-element blocks `|E| ≤ γ_{7 + ⌈log2(n/8)⌉} Σ|xᵢ|`; Neumaier `|E| ≤ u|s| + γ_{n−1}² Σ|xᵢ|` (Ogita–Rump–Oishi, *Accurate Sum and Dot Product*, Sum2, whose error-free step is what the branch computes). For n = 10⁶ (*computed*): γ_{n−1} = 1.1102·10⁻¹⁰; the pairwise index is 7 + 17 = 24, γ₂₄ = 2.66·10⁻¹⁵; γ_{n−1}² = 1.23·10⁻²⁰, so for positive data Neumaier's bound is `u|s|` plus a term 10⁻⁴ of it — about one unit in the last place. **Measured errors** (against `math.fsum`, in ulps of the exact sum): `tenths` — naive 91,595 ulps (1.33·10⁻⁶ absolute, relative 1.33·10⁻¹¹, about 12% of its bound), pairwise 0, Neumaier 0; `hashed` — naive 1, pairwise 1, Neumaier 0; `ramp` — all 0; `cancel` (Σ|x|/|s| = 10¹⁶) — naive and pairwise 1 (an error of 2.25·10¹⁵ ulps), Neumaier 0. The measured errors are far below the bounds because the bounds assume every rounding is the worst possible and all have the same sign; real roundings are spread over ±½ ulp and largely cancel, and the bound's job is to give a guarantee for *any* data, not to predict a run. **Why compensation needs strict evaluation.** `(sum − t) + x` is algebraically zero; only floating-point rounding makes it nonzero. A compiler allowed to reassociate (`-ffast-math`, `-fassociative-math`) may simplify it to 0, deleting the compensation, and may also vectorize and reorder the plain loops. *Measured* (an experiment; the flag is forbidden in this course's builds): with `-O2 -ffast-math`, GCC 11 gives `cancel` Neumaier = 1 instead of 2 and `tenths` Neumaier = 100000.00000133288, the same as the naive result; Clang 14 gives `cancel` = 1 and changes even the naive `tenths` result to 100000.0000001122 (a reordered vectorized sum). **Cost.** Naive: n additions. Pairwise: about n additions plus recursion overhead (small with 8-blocks), same operation count and better error. Neumaier: about 4 extra floating-point operations and a branch (or a conditional move) per element and a second live variable. Explicit grid: one multiply and one add per element instead of one add, and no dependency chain between elements. **When plain accumulation is exact or acceptable.** When every partial sum is exactly representable: integers whose partial sums stay below 2^53 (`ramp`), values that are multiples of a power of two with a bounded range (0.5 steps), and short sums where a bound of `k u` relative is enough. **The grid bound.** With `h = fl(0.1) = 0.1 (1 + δ₀)`, `δ₀ = 2^-54` exactly (`fl(0.1) = 3602879701896397 / 2^55` while `0.1 = 3602879701896396.8 / 2^55`, a relative difference of `0.2 / 3602879701896396.8 = 2^-54`), and `i` exact, the product `i·h` has relative error `δ₀` against `i/10` and its rounding adds `δ₁` with `|δ₁| ≤ u`; adding `start = 0` is exact. So `|x_i − i/10| / (i/10) ≤ δ₀ + δ₁ + δ₀δ₁ ≤ 1.5 u (1 + 2^-52)` — about one and a half unit roundoffs, as the plan states. The test asserts exactly this with `10·x_i` computed in `long double` (10·x_i needs at most 53 + 4 = 57 bits, so it is exact in a 64-bit significand, and so is the difference with `i`); gated on a wide `long double` and on Annex F. *Measured:* 1.4803·10⁻¹⁶ = 1.333 u, under the bound 1.665·10⁻¹⁶. The driver's own figure, 2.22·10⁻¹⁶, is measured against `(double)i / 10.0`, which is itself off by up to `u`, so it is not the accuracy of the grid but of a comparison between two rounded values. For the accumulated grid the test asserts the derived *upper* bound `(i + 1) u`, not that it is larger than the explicit error. **Integer counters.** The generator's microdegrees are integers: adding integers below 2^63 is exact in `int64_t`, and converting `micro` to `double` and dividing by 10⁶ is one rounding, never accumulated — the identifier `i` and the microdegree values are the accumulated quantity, and they never leave the integer domain until the last step. **Faulty compensation.** The update `c += (sum − t) + x` without the branch is right only when `sum` is the larger operand. *Measured* on `{1, 1e16, 1, −1e16}` (exact 2): naive 0, the branchless update 1, Neumaier 2; classic Kahan summation gives 1 on `{1e16, 1, −1e16, 1}` where Neumaier gives 2, because Kahan's error term is only valid while the running sum dominates.

### P02

**`r % 3`.** 2^32 = 3 · 1,431,655,765 + 1. The residues 1 and 2 each occur 1,431,655,765 times and residue 0 occurs 1,431,655,766 times, so the most likely residue is more likely than the least by a factor `1 + 1/1,431,655,765 ≈ 1 + 7·10⁻¹⁰`; the threshold `2^32 mod 3` is 1, and the rejected fraction is `1 / 2^32 = 2.3·10⁻¹⁰` (only the single value r = 0 is rejected). The bias is real but invisible in any sample this size — which is why the test can only check a 5% tolerance on 30,000 draws (a defect that big would be caught, this one would not). **`r % 3,000,000,000`.** 2^32 = 3,000,000,000 + 1,294,967,296, so each residue in `[0, 1,294,967,296)` occurs twice and each in `[1,294,967,296, 3·10⁹)` once: the ratio is exactly 2. The probability that `r % bound` is below 1,294,967,296 is `2 · 1,294,967,296 / 2^32 = 0.6030` instead of the uniform 0.4317 (*measured* 0.6029). The rejection threshold is 1,294,967,296; the rejected fraction is `1,294,967,296 / 2^32 = 0.3015`, and the expected number of raw draws per output is 1.4317. After rejection the accepted range has exactly 3,000,000,000 values, one per residue.

On the reference platform (x86-64, a gated observation: `sizeof(GeoPoint)` was *measured* as 24 bytes, i.e. `{uint64_t, double, double}` with 8-byte alignment and no padding, which is what the System V ABI prescribes; an ABI fact, not C11) the array at the cap is `1,000,000 × 24 = 24,000,000` bytes. ### P06

With `u = 2^-53 = 1.11·10⁻¹⁶` and `γ_k = k u / (1 − k u)`: naive `|E| ≤ γ_{n−1} Σ|xᵢ|`, which for n = 10⁶ is `1.1102·10⁻¹⁰ Σ|xᵢ|`; pairwise with 8-blocks `|E| ≤ γ_{7 + ⌈log2(n/8)⌉} Σ|xᵢ| = γ₂₄ Σ|xᵢ| = 2.66·10⁻¹⁵ Σ|xᵢ|` (a logarithmic, not linear, growth in n); compensated `|E| ≤ u|s| + γ_{n−1}² Σ|xᵢ|` with `γ_{n−1}² = 1.23·10⁻²⁰`, so for positive data `≈ 1.11·10⁻¹⁶ |s|`, one unit in the last place — the result is as accurate as the correctly rounded exact sum up to about an ulp, independent of n unless the data are badly conditioned (`Σ|xᵢ| / |s|` around 10⁴ or more makes the second term visible). *Measured* (n = 10⁶): `tenths`, naive 1.33·10⁻¹¹ relative (12% of its bound), pairwise 0 and Neumaier 0; `hashed`, all errors at most one ulp (2.1·10⁻¹⁶ relative). The measured errors are far smaller than the bounds because the bounds are worst cases over all inputs and all rounding directions: they add `n − 1` maximal rounding errors of the same sign, while real errors are spread over ±½ ulp and cancel (for random signs the expected accumulation grows like √n, not n) and here many partial sums are exactly representable. The bounds exist to give a *guarantee* that holds for any data (so a tolerance can be derived rather than guessed, as in this week's sum tolerance), to compare algorithms by how the guarantee scales with n (linear, logarithmic, essentially constant), and to say when the data (large `Σ|xᵢ| / |s|`) make a result untrustworthy.

### S02

[extras/repro_audit.py](extras/repro_audit.py) (part of `make verify`). It builds the E06 processor and the E07 summations with GCC 11.4 and Clang 14 at `-O0` and `-O2` under the strict flags and compares the printed output of all four builds. *Measured:* **the printed results are bit-for-bit identical in all four builds**, and no fused multiply-add instruction was generated (0 in each of the eight binaries). That is consistent with the flags (`-ffp-contract=off`), with the default x86-64 target (which has no FMA instruction to contract into) and with `FLT_EVAL_METHOD == 0` under SSE2; it is an observation about this machine and these two compilers, not a portability claim (a glibc that selects FMA variants of `sin`/`cos` at run time could differ on another CPU). **Optional FMA experiment**, gated on `/proc/cpuinfo` reporting FMA and AVX2, with `-ffp-contract=fast -march=x86-64-v3` (violating the week's rules only here): at `-O0` both compilers still generate no FMA; at `-O2` GCC generated 5 (processor) and 2 (sums) fused instructions and Clang 4 and 22. *Measured*: the printed output was nevertheless **identical** to the strict output — the processor prints six decimals of its sum, which hides a last-digit change, and the sums are dominated by additions, which contraction does not touch (`x + i * step` with `start = 0` is the same either way). So the cautious conclusion is *no difference observed at the printed precision on this machine*, not “contraction is harmless”. What would change: a contracted `a * b + c` is rounded once instead of twice, so a result can differ in its last bit; a comparison at a floating-point boundary (E06's inclusive radius) is where such a difference could flip a decision. Two further reasons results can differ across machines even with identical source and flags: libm may pick different algorithm variants at run time (some glibc builds choose FMA versions of `sin` and `cos` by CPU), and a different libm version may round transcendental functions differently — which is why no test compares them bit for bit.
