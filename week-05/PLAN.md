## Why this week exists

Weeks 1–4 produced correct pieces. Week 5 turns them into the first **section project**: one `geolab` program, built from several translation units, whose `generate`, `query` and `bench` commands have written contracts, fixtures, an independent oracle and a report. The new idea is **measurement as an experiment**. A timing is an observation of one build of one program on one machine under stated conditions; it becomes evidence only when the result was checked correct first, the conditions were recorded, the prediction was written down before running, and the variation was measured rather than assumed away. The Computer, Enhance! prologue entries (“Single Instruction, Multiple Data,” “Caching,” “Python Revisited”) show how large the differences between implementations of the same computation can be; Handmade Hero 010, 112 and 113 show how to reason in cycles and time budgets and how to measure before optimizing. This week does not reproduce any of those multipliers. It records a **scalar baseline** that later weeks (13, 23, 25, 31–35, 42) will compare against, and it establishes the scalar-with-vectorization-disabled build that the vectorization path begins from.

By the end, a learner should be able to assemble a multi-file C program with a documented command-line contract and explicit exit codes; implement a query whose output order is a total, deterministic function of the input; design fixtures that each exist for a stated reason; distinguish wall time, processor time and cycle counts and say which clock measures which; write and follow a timing protocol with warm-up, repetitions, process-level reruns and a stopping rule fixed in advance; summarize samples with order statistics and explain why; and write a report that keeps **correctness, prediction, observation and uncertainty** in separate sections.

Do not add later-week topics: RDTSC or other counter experiments and nested profiling (weeks 13–14), cache or working-set sweeps (22), layout comparisons (23), a binary format or `mmap` (25), dead-code-elimination demonstrations (30), SIMD, intrinsics or attempts to make the compiler vectorize (31–35), threads (36–42), or spatial indexes (43, 45). The `--threads`, `--backend` and `--index` options exist only so the command line is stable; this checkpoint accepts exactly `1`, `scalar` and `none`. **There is no speedup threshold, and a faster number is never, by itself, a better grade.**

## Corrections incorporated after implementation

**2026-09-22 plan review, before implementation:** The normative requirements below include these corrections. Week 4's loader accepts a header-only file, so `bench` now has an explicit zero-row policy; otherwise `median_ns_per_point` divides by zero. Identical input coordinates give an exact distance tie without assuming an odd `libm` sine implementation. A write error can occur after output has begun, so the empty-stdout guarantee applies to validation and computation failures, while output errors are reported separately. The bench checksum is a useful observable check, not a proof that all work ran or that two results are equal. The timed boundaries and benchmark build artifacts are specified so the comparison can actually be reproduced. The existing Week 4 data cap of 1,000,000 rows and error statuses remain in force.

**2026-09-22, found during implementation** (evidence in [validation.md](instructor/validation.md)):

- **`generate` must not remove a path it did not create as a regular file.**
  - *What happened:* week 4's `write_csv_file` calls `remove` after any failure that follows a successful `fopen`. A path such as `/dev/full` opens and then fails every write, and with enough privilege the device node would be deleted.
  - *The fix:* the reference removes the partial output only when `stat` reports a regular file (POSIX `S_ISREG`).
  - *Tests:* `--out /dev/full` (the device survives), and a symbolic link to `/dev/full` owned by the test (the link survives). The mutation check showed the link test is needed, because a non-root test cannot observe an attempt to remove `/dev/full` itself.
- **`VEC=default` does not vectorize anything with GCC 11.**
  - GCC 11.4 disables `-ftree-loop-vectorize` and `-ftree-slp-vectorize` at `-O2`, so every GCC object is byte-identical between `VEC=off` and `VEC=default`.
  - With Clang 14 only `csv.o` differs, and the distance loop is not vectorized by either compiler (“control flow in loop”; “call instruction cannot be vectorized”).
  - The E06 build comparison is therefore an A/A test of run-to-run variation for GCC. The answer key and report use it that way: a single smoke run showed a 25% difference between identical machine code.
- **A single global oracle tolerance would have made the printed-tie fixture untestable.**
  - The plan's “justified tolerance” was implemented as a banded rule: 1e−10 km below 15,000 km, 1e−8 below 19,900 km and 5e−7 beyond.
  - Each band is at least eleven times the largest disagreement measured between the haversine and the vector formula on 909,000 pairs. The nearly antipodal worst case is 4.1e−8 km.
  - A global 5e−7 km would treat every pair closer than 1e−6 km as unordered, including the printed-tie pair, which is 3.8e−7 km apart.
- **An empty dataset still needs its center validated.** The first reference returned success for `query_points(NULL, 0, 95, …)`, because its empty-input shortcut came before validation. Mutation testing found it; the reference and the suite were fixed.
- **Where the learner's fixtures live and what `bench` plumbing is supplied.** “Write `fixtures/README.md`” is implemented per package (`learner/fixtures`, `instructor/fixtures`), so that the exemplar does not give the answer away. For the same workload reason (A5), `cmd_bench`'s option handling and printing, `bench_format_checksum` and `cli_check_future_options` are supplied plumbing. The learner implements `summarize_ns` and the measurement kernel `bench_measure`, which contain every timing decision E04 asks about.
- **Bench defaults and the checksum token.**
  - The plan left `bench`'s optional center and radius without defaults. They are (0, 0) and 1,000 km, recorded in [CHECKPOINT-1.md](CHECKPOINT-1.md).
  - The checksum is printed as one token `COUNT:VALUE`, so that the bench line stays `key=value` pairs.
  - The query hash starts from 14695981039346656037, a detail the plan left open.
- **Timing observation that contradicted the plan's expectation.** At 1,000 points both `distance` and `query` cost about 25% less per point than at 100,000 and 1,000,000 points, with non-overlapping ranges in five runs. The answer key records this as an observation with hypotheses (working set in L1; trained branch predictors) for weeks 22 and 27, not as a cause.
- **Time-consuming environment note.** As in weeks 3 and 4, builds on the OneDrive-backed `/mnt/c` checkout are slow. The mutation check (46 mutants, about 45 minutes) was run from a copy in the WSL home directory.

## Constraints carried forward from earlier reviews

The week-2 and week-4 lessons still apply: verify every claim; state overflow contracts for sums as well as products; state explicit limits; validate before committing outputs; gate reference-platform observations (`__STDC_IEC_559__`, `sizeof(double) == 8`, and here also `__linux__` for `/proc` and `CLOCK_MONOTONIC` details) with a forced-skip build (`-DGEO_FORCE_NO_IEC`); sequence side effects in separate statements; give learners typed, warning-clean TODO functions and supplied plumbing; justify every tolerance by a derivation or a measurement with at least a ten-fold margin; mutation-test the harness and classify survivors as equivalent mutants or real gaps.

The [week-3 review](../week-03/actions.md) found defects that a passing suite had not revealed. Its five actions are generalized here and checked in the acceptance section:

- **Derive results from the original data, not from a lossy intermediate (A1).** Query order is decided by the unrounded `double` distance and the identifier, never by the printed six-decimal text; the inclusive-radius test compares the computed distance with the parsed radius, never a rounded value. Timing statistics are computed from the integer nanosecond samples, never from a formatted value. Tests include inputs chosen to expose a lossy shortcut: two hits whose printed distances are equal but whose unrounded distances differ in the order opposite to their identifiers.
- **Check every proof step against a counterexample search (A2).** Each derived bound (nanosecond conversion overflow, median arithmetic, checksum properties, the fixed-point conversion of command-line numbers) is written as a proof and then attacked with the extreme values of its domain before it is published. A test illustrates a proof; it does not replace one.
- **Separate exact, correctly rounded and tolerance-assessed results (A3).** Integer outputs (counts, identifiers, order, checksums over integers, nanosecond arithmetic) are exact. The conversion of `-33.868800` to a `double` is correctly rounded under Annex F, which is not the same as exact. Distances involve `libm` and are compared with a justified tolerance. Timings are observations with a measured spread and are never asserted by a test. Do not describe a surviving mutant as equivalent on the evidence of samples alone.
- **Use precise terms and demonstrate them (A4).** Distinguish wall-clock time, processor time and cycle counts; latency and throughput; a measured difference and its cause; SIMD (a hardware capability) and vectorization (the transformation of a loop). A learner who writes “cache effect” or “the compiler vectorized it” must cite evidence of the mechanism (a diagnostic, a disassembly, a counter) or label the statement as a hypothesis.
- **Keep the workload credible and the uncertainty explicit (A5).** The independent query oracle, the monotonic timer and the environment reporter are **supplied**; the learner explains why the oracle is independent, traces one case through it, and adds a few purposeful fixtures, but does not write a second oracle. The estimate below is unpiloted; the validation record says so and includes the pilot procedure from the acceptance section. Agent execution time is never presented as learner completion time.

Build the `VEC=off` and `VEC=default` executables at distinct paths so an interleaved protocol never silently reuses or overwrites the wrong variant; record the complete compile command for each.

## The `geolab` checkpoint-1 command line

- `geolab generate --count N --seed S --out FILE` — week 4's contract and bytes, unchanged; the oracle digests from week 4 still apply.
- `geolab query --input FILE --lat X --lon Y --radius-km R [--threads 1] [--backend scalar] [--index none]` — prints `id,distance_km` and then one `ID,D` line per point whose distance is `<= R` (inclusive), ordered by the unrounded distance ascending and then identifier ascending; `D` is printed with `"%.6f"`. The program never calls `setlocale`, so it runs in the `"C"` locale (C11 §7.11.1.1 ¶4) and the decimal point is `.`. Under Annex F.5 ¶2 a value below 20,016 printed with six decimals (at most 11 significant digits) is correctly rounded; that claim is gated and labelled.
- `geolab bench --input FILE --variant parse|distance|query --repeat N [--warmup W] [--lat X --lon Y --radius-km R]` — prints one environment block and one line `bench variant=V points=P warmup=W repeat=N resolution_ns=… min_ns=… median_ns=… max_ns=… median_ns_per_point=… short_samples=K checksum=…`.
- **Numbers on the command line.** `--lat`, `--lon` and `--radius-km` accept `-?(0|[1-9][0-9]*)(\.[0-9]{1,6})?` (the radius without a sign), are accumulated as integer micro-units with checked arithmetic, range-checked (latitude to ±90, longitude to ±180, radius to `[0, 100000]`, as week 4's `process_points`), and converted by one division by `1e6` (correctly rounded under Annex F, as week 4 E04 argued). A negative zero such as `-0.0` is accepted and yields `+0.0`; the answer explains why a command line may be more lenient than a dataset format and why this one is not lenient about anything else. `--count`, `--seed`, `--repeat` and `--warmup` are decimal unsigned integers without sign or whitespace; `--repeat` is 1–1,000 and `--warmup` 0–100 (default 3).
- **Exit codes:** 0 success; 1 input, data, allocation, clock or output error (unreadable or malformed files include week 4's status name and line number); 2 usage error (unknown, duplicate or missing option; malformed or out-of-range value); 3 an option value this checkpoint does not support (`--threads` other than 1, `--backend` other than `scalar`, `--index` other than `none`). Every diagnostic goes to standard error and begins with `geolab:`. Validate and compute the complete result before printing, so standard output is empty on validation and computation failures. A failed write to standard output can leave a partial result; check `fprintf`/`fwrite` and `fflush` and report that failure without promising rollback. `bench` rejects a valid header-only input with exit 1 and `geolab: empty benchmark input`, because nanoseconds per point is undefined for zero points; `query` still accepts it.

## Assessment and acceptance criteria

The checkpoint **passes** only if `make checkpoint` succeeds with the learner's code, every command meets its contract, and the report separates correctness, prediction, observation and uncertainty. A passing project is then scored:

- **Functional correctness (40%):** E01 6, E02 12, E03 4, E04 8, E05 3, E06 2, E07 5. Correct results, errors, exit codes and diagnostics; outputs unchanged on rejection; no leak on any error path; strict builds on both compilers.
- **Measurement method (25%):** Five points each for a protocol written before data collection and followed; recorded environment and build variants; correctness established before timing with checksums enforced; variation measured and reported with the stated range comparison and its limits; honest handling of short samples and outliers.
- **Reasoning and explanation (20%):** Five points each for the query's ordering argument; the oracle and fixture reasoning; the prediction model; and the claim ledger's labelling of C11, POSIX/Linux, compiler, hardware and observed statements.
- **Clarity (15%):** Source, diagnostics, the protocol and the report can be understood without the videos open beside them.

No points depend on speed, on a prediction being accurate, or on matching the exemplar's numbers; a prediction that missed and was reconciled honestly earns full credit.

Acceptance checks for the agent implementing this week: every milestone has learner instructions, a tested reference solution and a full written answer to every question; all practice problems, both stretch exercises and every report prompt have worked answers; an inventory script confirms the exact set of 26 IDs; strict builds pass with both compilers at `-O0` and `-O2`, and the reference project passes under AddressSanitizer and UndefinedBehaviorSanitizer with no leak on any error path; **`generate` remains byte-identical to week 4's oracle**; **the query oracle is independent of the reference, self-tested against known-answer vectors, and compared exactly only where its tolerance rule allows**; **the exact-tie fixture uses identical coordinates, and the Annex F printing claim is checked under its gate**; **the printed-tie fixture fails a sort by printed value** (demonstrated by a mutant); **the header-only benchmark, write-error policy and two separate benchmark binaries are tested**; **every derived bound (median, nanosecond arithmetic, command-line accumulation) has a proof checked against its extreme values**; **no test asserts a timing**, and every timing quoted in the answer key or exemplar report is labelled with its machine, build and date; the forced-skip build exercises the gates; the learner skeleton compiles warning-clean and fails `make test` for unimplemented behavior rather than a build or harness error; mutation testing of the harness has been run and its survivors classified in the validation record; every reading link and indexed segment is re-verified.

The core target is 600 minutes: 160 for viewing and reference consultation, 15 for setup, 285 for the milestones (E01 35, E02 55, E03 35, E04 55, E05 40, E06 40, E07 25), 55 for the report, 30 for practice, and 55 for debugging. Stretch work and optional viewing are additional. The E06 timing runs execute unattended inside the E06 time.
