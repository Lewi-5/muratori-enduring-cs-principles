## Why this week exists

`geolab` is a data engine, and a data engine needs data whose provenance is not in doubt. Week 4 builds the two ends of the pipeline that every later week reuses: a **deterministic generator** that writes a dataset as a pure function of `(seed, count)`, and a **strict parser and scalar reference processor** that reads it back and computes the Haversine distances. Three ideas run through it. *Determinism* is engineered: the generator uses only integer arithmetic with defined wraparound, formats text from integers rather than from `printf("%f")`, and fixes the order in which random values are drawn, so the bytes are identical under every compiler and optimization level. *Parsing* is a contract: a canonical grammar, explicit error classes, bounded reads, and exact conversion from text to `double`. A *reference implementation* is the simple, obviously correct version that later, faster versions must agree with; it earns that role by being written by a different method and checked against an independent oracle. The Handmade Hero “accumulation versus explicit calculation” lesson supplies the numerical lesson: adding many small values, or repeatedly adding a step, accumulates rounding error that computing each value directly does not.

This week does **not** measure speed. The Computer, Enhance! “Clean Code, Horrible Performance” entry is assigned as motivation for asking how representation and structure affect cost; its headline multipliers come from one program on one machine and are not adopted here. Timing arrives in week 5, and layout comparison in week 23.

By the end, a learner should be able to explain how a reproducible dataset is produced and why it stays reproducible across builds; generate an unbiased bounded integer from a raw generator and explain modulo bias; format and parse fixed-point decimal text without floating-point printing or parsing; write a bounded, leak-free file loader with explicit errors; and explain how the order and method of summation change a result and how to check one against an exact reference.

Do not add later-week topics: a timing protocol or benchmark (weeks 5, 13), the `query` command with ordering by distance then ID (week 5), a binary format or `mmap` (25), a streaming parser or a better PRNG with entropy tests (47), spatial indexes, SIMD, or threads. The processor here is a scalar loop with no speed claim.

## Corrections incorporated after implementation

Implementing and verifying this week found the following errors, ambiguities or gaps. The requirements table below and the linked learner package state the current contracts; these notes preserve the correction history.

- **2026-09-22 review:** the general NULL-output rule also applies to `parse_record`; NULL `line` or `out` now returns `PARSE_INVALID_ARGUMENT` before examining the grammar. `grid_accumulated` stops stepping after its last requested element, and the E07 driver frees either grid allocation on setup failure. The status order for non-NULL CSV lines is unchanged. Fresh verification is recorded in [validation.md](instructor/validation.md).

- **Annex F clause.** The plan cites “Annex F.5 (conversion between binary and decimal)”. In N1570 the section is F.5 “Binary-decimal conversion” and the operative sentence is **¶2**: conversion between an IEC 60559 format and decimal with `DECIMAL_DIG` or fewer significant digits is correctly rounded (checked against the extracted N1570 text). ¶3 adds that `strtod` honors the rounding direction, which is why the negative case follows by symmetry only in round-to-nearest.
- **A status for NUL bytes.** E05 requires NUL bytes to be errors but the status list has none, and a NUL cannot reach `parse_record` (a C string ends at it, so a truncated line could even be accepted). The supplied `ParseStatus` gains `PARSE_NUL_BYTE`.
- **Ordered error classes are field by field.** “The same for longitude” leaves open whether every latitude *and* longitude grammar error precedes range errors. The package fixes the order as empty, field count, identifier, latitude grammar, latitude range, longitude grammar, longitude range, so `1,91.000000,bad` is `PARSE_LAT_RANGE` and `12,100.000000,200.000000` is `PARSE_BAD_LAT`. The oracle encodes the same order independently.
- **Empty summation.** “`returns 0` for `n == 0`” is ambiguous with the status convention (0 = rejected). The package defines `n == 0` as success with `*out = 0` for the three sums, and `n == 0` grid calls still validate `start` and `step`.
- **Loader details the plan left open.** The initial capacity is `min(1024, GEOLAB_MAX_ROWS)` (otherwise a cap below 1,024 would be exceeded); `PARSE_TOO_MANY_ROWS` is reported only for a *valid* row that does not fit, so a malformed extra row reports its own status and a trailing blank line reports `PARSE_EMPTY`; the first offending byte or line decides the status; a failing `fclose` after a good parse is `PARSE_IO_ERROR` with line 0; an empty file reports line 1; on success `*err` is `{0, PARSE_OK}`. Reaching the doubling clamp needs a second cap-lowered build (`GEOLAB_MAX_ROWS = 1500`, capacities 1,024 then 1,500) in addition to the plan's cap of 8.
- **`remove` after a failed `fopen` is a bug.** `remove()` on an empty directory deletes it (POSIX), so the plan's “on any failure removes the partial file” must not apply when `fopen` itself fails; the test opens a directory as the path and requires that it survives. `fopen("wb")` also truncates an existing file, so a failed generation loses its previous contents; the plan is silent, the answer states the limitation.
- **Termination of `lcg_below`.** The plan asks for “a finite worst case”. The only proven deterministic bound is crude: fewer than 2^63 consecutive rejections (accepted states outnumber 2^63 in a cycle of 2^64), which is finite but useless. The useful statement is probabilistic, with the accepted fraction always above one half (`2^32 mod bound < 2^31`) and measured longest rejection runs of 16 (bound 3·10⁹) and 23 (bound 2^31 + 1) in 10^8 draws.
- **Random sampling cannot see an off-by-one at the threshold.** A mutant that rejects `r <= threshold` differs from the correct code once in 2^32 draws. The tests therefore add oracle states, found by inverting the recurrence (`A` is odd, so it is invertible modulo 2^64), whose next output is exactly `threshold − 1`, `threshold` and `threshold + 1`.
- **The E07 grid bound is against the exact quotient.** The plan measures both grids “against `(double)i / 10.0`”, but the bound of about 1.5 `u` holds against the exact rational `i/10`, not against a reference that carries its own rounding: measured against the double reference the explicit error is 2.22·10⁻¹⁶ (2 `u`), against the exact quotient 1.48·10⁻¹⁶ (1.33 `u`). The driver keeps the plan's reference; the test computes the exact comparison in `long double` (`10·x_i` needs at most 57 bits, so it is exact) and asserts `≤ 1.5 u (1 + 2^-52)`, gated. The exact `fl(0.1)` error is `δ₀ = 2^-54`.
- **The sum tolerance needs a second term.** The plan justifies the E06 sum tolerance by the `n·u` accumulation bound alone. Measured, haversine and the unit-vector reference disagree by up to 3.3·10⁻⁹ km on nearly antipodal pairs (a week-3 conditioning effect, in the haversine), so the tolerance 2·10⁻¹² relative combines the derived accumulation bound (1.11·10⁻¹²) with a measured per-point term (at most 3.3·10⁻¹³). The `min_km`/`max_km` tolerance was first set to 10⁻¹², only 1.2 times the measurement, and was raised to 10⁻¹¹ to keep the ten-fold margin the policy requires.
- **Classic Kahan summation is not the plan's compensated sum.** On `cancel` classic Kahan gives 1 (measured) where the Neumaier form gives 2; the plan's “whichever operand is larger” requirement is what the branch provides, and the tests use the four orderings of the `cancel` numbers, because a compensation without the branch passes the plan's own single ordering and fails the reordered one (found by mutation testing).
- **The equivalence of redundant checks.** Mutation testing showed several behaviorally equivalent variants: dropping only the `fputs` result check, only the final `ferror`, or only the header write check (each is sufficient with the others), dropping the `n > 20` identifier length check (the overflow guard rejects 21-digit numbers anyway), and validating only the first point (the haversine validates each point again before anything is written). The byte-count check before `realloc` is unreachable on a 64-bit target with the course cap. These are recorded in the validation record rather than “fixed” with tests that would assert an implementation detail.
- **Readings and links.** All links, the durations of the four Computer, Enhance! entries (22:40, 15:40, 12:09, 29:22) and the Handmade Hero 146 segment boundaries (42:07, 44:46, 50:11, 56:04) were re-verified on 2026-09-21; Goldberg's summation material is the section “Errors In Summation” (with Theorem 8 on Kahan's formula). The de_DE locale needed to *reproduce* the locale-dependent decimal point is not installed on the reference machine, so that claim is cited to the standard and labelled as not reproduced.
- **Time-consuming environment note.** As in week 3, Clang's sanitizer configuration takes several minutes on the OneDrive-backed `/mnt/c` checkout and about a second per compile elsewhere; this is a filesystem cost, not a test property.

## The `geolab` CSV v1 format and generator (definitions used by all exercises)

- **File:** UTF-8-compatible ASCII, LF line endings only (never CRLF), no BOM, no quoting, no spaces. First line exactly `id,lat_deg,lon_deg`. Every following line is `ID,LAT,LON` followed by `\n`; the last line ends with `\n` when generated. A final line without a newline is accepted by the parser.
- **`ID`:** `0` or a decimal number without leading zeros, at most 20 digits, at most `UINT64_MAX`. **`LAT`:** an optional `-`, then an integer part `0` or `[1-9][0-9]?`, then `.`, then **exactly six** digits; magnitude at most 90.000000. **`LON`:** the same with an integer part of up to three digits and magnitude at most 180.000000. `-0.000000` is not canonical and is rejected. Coordinates are therefore whole numbers of **microdegrees** (`lat_udeg` in `[-90000000, 90000000]`, `lon_udeg` in `[-180000000, 180000000]`).
- **PRNG (deliberately simple; replaced in week 47):** a 64-bit linear congruential generator with state `s`, advanced *before* each output: `s = s * 6364136223846793005 + 1442695040888963407` modulo 2^64 (unsigned wraparound is defined), output `(uint32_t)(s >> 32)`. The multiplier is congruent to 1 modulo 4 and the increment is odd, so by the Hull–Dobell theorem the generator has full period 2^64; the implementing agent verifies both conditions. The low bits of a power-of-two-modulus LCG have short periods, which is why only the high 32 bits are used. The initial state is the seed.
- **Generation:** for row `i` from 1 to `count`: id `i`; draw `r` with `lcg_below(180000001)` **into its own variable**, then `lat_udeg = r - 90000000`; then draw `r` with `lcg_below(360000001)` into its own variable, then `lon_udeg = r - 180000000`. The two draws are separate statements because argument evaluation order is unspecified. Coordinates are uniform in *degrees*, so points cluster toward the poles per unit area (the area element is proportional to the cosine of latitude); this is a property of the dataset, not a bug.
- **Course cap:** `GEOLAB_MAX_ROWS`, 1,000,000 rows, defined with `#ifndef` so tests can lower it. **Maximum line length:** 127 characters excluding the newline (`GEOLAB_MAX_LINE`); the longest generated line is 43 characters.

## Constraints carried forward from the week-2 review

The week-2 plan was reviewed and corrected before this one was written. The following lessons apply here and are checked in the acceptance section:

- **Verify every claim.** No exercise assumes a result it has not proved or measured. Where the plan says a summation is “expected to lose accuracy,” the answer key must measure it against an exact oracle and label the values as measured. No error size is asserted without a derivation or a recorded run.
- **State overflow and range contracts for sums as well as products.** Every integer computation that can overflow is bounded or checked: digit accumulation (`value * 10 + digit` is guarded by comparing `value` with `(UINT64_MAX - digit) / 10`), buffer sizes, capacity growth (`capacity * sizeof(GeoPoint)` and doubling are both checked), and microdegree arithmetic (widened before subtracting the offset; `INT32_MIN` is never negated). Signed overflow is never relied on. Floating-point overflow is well defined but each function states what it returns.
- **State explicit limits.** Zero counts, the row cap, the seed's full 64-bit range, accepted `limit` values, maximum line length, and buffer sizes are specified. A function that reports failure leaves its outputs unchanged (for arrays: validate, then commit).
- **Gate reference-platform observations.** Claims that rest on Annex F conversions (the exactness of text-to-double), glibc, or x86-64 struct sizes are labelled and gated (`__STDC_IEC_559__`, `sizeof(double) == 8`). A forced-skip build (`-DGEO_FORCE_NO_IEC`) tests the gating path.
- **Sequence side effects.** No exercise depends on argument evaluation order; every PRNG draw is its own statement (see above).
- **Workload honesty.** Learners receive typed, warning-clean TODO functions and supplied demo drivers, the supplied `GeoPoint` and status types, and supplied argument-parsing plumbing; the learner implements the mechanisms. The estimate is unpiloted.
