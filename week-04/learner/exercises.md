## The `geolab` CSV v1 format, the generator and the caps (used by every exercise)

- **File.** ASCII, LF line endings only (never CRLF), no byte-order mark, no quoting, no spaces. The first line is exactly `id,lat_deg,lon_deg`. Every following line is `ID,LAT,LON` followed by `\n`; a generated file ends with `\n`, and the parser also accepts a final line without one.
- **`ID`** is `0` or a decimal number without leading zeros, at most 20 digits, at most `UINT64_MAX`. **`LAT`** is an optional `-`, an integer part `0` or `[1-9][0-9]?`, a `.`, and **exactly six** digits; the magnitude is at most `90.000000`. **`LON`** is the same with an integer part of up to three digits and magnitude at most `180.000000`. `-0.000000` is not canonical and is rejected. Coordinates are therefore whole numbers of **microdegrees**: `lat_udeg` in `[-90000000, 90000000]` and `lon_udeg` in `[-180000000, 180000000]`.
- **PRNG** (deliberately simple; replaced in week 47): a 64-bit linear congruential generator with state `s`, advanced *before* each output: `s = s * 6364136223846793005 + 1442695040888963407` modulo 2^64, output `(uint32_t)(s >> 32)`. The initial state is the seed.
- **Generation.** For row `i` from 1 to `count`: the identifier is `i`; draw `r` with `lcg_below(180000001)` **into its own variable**, then `lat_udeg = r - 90000000`; then draw `r` with `lcg_below(360000001)` into its own variable, then `lon_udeg = r - 180000000`. The two draws are separate statements because the order in which function arguments are evaluated is unspecified. Coordinates are uniform in *degrees*, so points cluster toward the poles per unit area; that is a property of the dataset, not a bug.
- **Caps.** `GEOLAB_MAX_ROWS` (1,000,000, defined with `#ifndef` so tests can lower it) and `GEOLAB_MAX_LINE` (127 characters excluding the newline; the longest generated line is 43). Both are in [support/geolab_types.h](../support/geolab_types.h), which also supplies `GeoPoint`, the `ParseStatus` enumeration, and `parse_status_name`. [support/reference_distance.h](../support/reference_distance.h) supplies a plain unit-vector distance used only by the E06 driver.

General contract. Every function that reports a status returns 1 on success and 0 on rejection unless a prompt says otherwise. **A rejected call leaves every output object unchanged**; for functions that fill several outputs or an array, validate everything first and commit last. A NULL output pointer is a rejection. Never rely on signed integer overflow, on the evaluation order of function arguments, on `errno` from math functions, or on the locale. Library code never prints or exits. Every integer computation that can overflow is bounded or checked, for sums as well as products.

Build flags are `-std=c11 -Wall -Wextra -Wpedantic -Werror -ffp-contract=off` at `-O0` and `-O2`, linking `-lm`. **`-ffast-math`, `-Ofast`, `-funsafe-math-optimizations` and `-march=native` are forbidden**: they allow reassociation and fused multiply-add, and E07 studies exactly the arithmetic they would change. Floating-point tolerances in the tests come from [tests/tolerances.h](../tests/tolerances.h) and are never bit-for-bit libm expectations. The one place fixed expected outputs are legitimate is the file format itself, which is fully specified and platform-independent: [tests/oracle.py](../tests/oracle.py) is an independent implementation of the LCG, the formatter, the grammar and exact summation, and the tests compare against it.

Claims that rest on Annex F conversions or on the x86-64 layout of `GeoPoint` are gated on `__STDC_IEC_559__` with a 64-bit `double` (see [support/platform.h](../support/platform.h)) and report "skipped" elsewhere; `-DGEO_FORCE_NO_IEC` exercises the skip path and does not emulate another platform.

### E01.C

Implement `uint32_t lcg_next(uint64_t *state)` exactly as specified above, and `int lcg_below(uint64_t *state, uint32_t bound, uint32_t *out)`. `lcg_below` rejects `bound == 0` (and a NULL pointer) leaving the state and the output unchanged; otherwise it draws until `r >= threshold`, where `threshold = (uint32_t)(0u - bound) % bound`, and sets `*out = r % bound`. That is rejection sampling to avoid modulo bias. The driver stores every draw in its own variable and prints `seed=0 first=XXXXXXXX,XXXXXXXX,XXXXXXXX` (hexadecimal) and `bound7=` followed by ten draws below 7. Test: the first 1,000 outputs for seeds 0, 1 and `UINT64_MAX` against the oracle; `lcg_below` for bounds 1, 3, 7, 3,000,000,000 (which rejects about 30% of raw draws, so the retry path runs) and `UINT32_MAX`, including how many raw draws were consumed; bound 0 rejected; every output below its bound; for bound 3 over 30,000 draws no residue's count differs from the mean by more than 5%.
